# Correction round: a bounded automatic correction after a blocking review

Status: implemented 2026-10-08 with fake clients (plan 2026-10-08-correction-round); §6 live verification run 2026-10-08/09 on `06bb054`: run 6 (`accept_on_high: true`) reached the first unattended `done` with no blocking review (correction `trivial`); run 7 (`accept_on_high: false`) exercised the correction round live (critical review → driver-prepared correction with the recorded decision, the frozen input and the finding → in-place correction → re-bundle → re-review without the critical → `needs-human/open-high-findings` with `corrections: {used: 1, max: 1}`), after three documented interventions caused outside the coordinator. Run 8 proved the kill-and-restart continuation (`drive_loop` restart after a SIGKILL, `done`, all criteria pass). Copilot smoke 6 (2026-10-09) reached `done` with two corrections of the architecture by a Copilot author, with two inbox decisions in between; a zero-intervention `done` that includes a correction remains unproven live. Extends the [unattended driver design](unattended-driver-design.md) §5, §6 and §7 and takes the first item of its §11 follow-ups out of "not in scope". Nothing here changes a numbered decision of that design: D13 still says that a critical finding, and a `high` one without `accept_on_high`, blocks acceptance; this design adds what the driver may do *before* it gives up, never a lower threshold. Run 9 (2026-10-09, author and judgment `codex-cli`, reviewer opus, `accept_on_high: false`, `max_corrections: 2`): two corrections of a Codex-authored PRD (the first asked a question instead of silently changing a rule, the second cleared a critical and a high), acceptance, `done`; two `judgment-budget` stops recovered with inbox decisions.

## 1. Problem

A bound review that rates a finding `critical`, or `high` while the pipeline leaves `accept_on_high` at `false`, ends the run `needs-human` (`critical-finding`, `open-high-findings`). The operator then releases, corrects and re-reviews attended, and starts again. The live hook (run 4) stopped exactly there: a real PRD defect (a decimal grammar admitting `007.5` against the recorded answer `LZ1`), rated critical by an opus reviewer, after ten clean turns. An unattended `done` has therefore never been reached live. The attended path already has the piece the driver lacks: `bmad prepare` with `intent: update`, `update_of` an observed completed attempt and a `change_signal`, which the planning brief labels as caller-reported text.

## 2. Goal and non-goals

**Goal.** When a recorded review blocks acceptance, the driver prepares and launches a bounded number of correction attempts of the authoring step, each carrying the blocking findings from the stored review row, and lets the existing derivation re-bundle, re-review and accept. When the budget is spent and findings still block, the run stops exactly as today, saying how many corrections it tried.

**Non-goals.** The acceptance threshold is unchanged (medium and low never block; `accept_on_high` keeps its meaning). The re-review is a fresh review of the corrected bundle: the earlier review's findings are not carried into it for disposition (a follow-up). A correction never targets an accepted bundle, an earlier mandate revision or another step's artifacts (an architecture is not corrected against its PRD). Pipeline supersession, partial decisions and worker-steered judgment are unchanged. No new reason code, state or table.

## 3. Decisions

**D1. Budget `max_corrections`.** `budgets` gains the optional key `max_corrections`, an integer `0`–`4` (`MAX_CORRECTIONS = 4`), default `0`. A pipeline without the key validates, seals and digests exactly as today, so bound pipelines and their recorded digests are unchanged. The budget is counted per author step as the number of bound planning attempts of that step (skill and workspace, current mandate revision, not cancelled) whose binding has `continues.corrects_review`. Every prepared correction counts, whatever its outcome.

**D2. Trigger.** A correction is prepared for an author step when all of these hold at the current mandate revision: its head is an observed `completed-claim` with a complete or partial verdict; the newest bundle naming that head as a source has an observed recorded review; that bundle has no acceptance; the review has blocking findings; and the step's corrections used are below `max_corrections`. The *blocking findings* of a review are the JSON pointers (`/findings/<i>`, `/dispositions/<i>`, in the recorded view's order) of every item rated `critical`, plus every item rated `high` unless the pipeline sets `accept_on_high`. This is the same predicate that makes the accept step stop today, so a correction targets precisely what blocks acceptance. When the trigger does not hold, the author step is `satisfied` as today. A bundle with more than one review row (reachable only through attended extra reviews) is read differently by the two steps: the trigger reads the newest observed review, while the accept step blocks on any open critical row; an older or reported critical review therefore stops the run without a correction (fail-safe).

**D3. Prepare continuation `corrects_review`.** `PlanningPrepare` gains `corrects_review: str | None` and `finding_ids: list[str]` (update only). An update now requires `update_of` and `continues_request`, a non-blank `change_signal`, or `corrects_review` with a non-empty `finding_ids`; `corrects_review` excludes the other two, while the pre-existing `continues_request` + `change_signal` pair stays accepted as today; a create allows none of them. `prepare` checks that `update_of` is an observed `completed-claim` of the same feature and skill (the `change_signal` rule), that the review exists, is `observed`, and is of a bundle at the current mandate revision whose sources name `update_of`, and that every pointer in `finding_ids` resolves in the recorded review view to a finding or a disposition (`INVALID_INPUT` otherwise; duplicates refused). The binding records `continues = {"update_of", "request": null, "corrects_review", "finding_ids"}`. The attended command takes the same fields through its JSON spec; no new CLI flag.

**D4. Brief.** The continuation section of the planning brief, for a correction, reads "Correction after a recorded review" and is rendered from stored rows only (the review row's id, bundle id and reviewer id; each named item verbatim with its pointer, severity and, for a finding, `lens` and `location` in backticks and `trigger_condition`, `guard_snippet`, `potential_consequence` JSON-quoted (so a multi-line field cannot end the list or forge a heading); for a disposition, `contributor_id`, `kind`, `index`), with these rules: the items are the reviewer's recorded claims, not decisions; correct the earlier files in place so that each item no longer holds; a correction that would need a decision no recorded decision covers becomes an `open_questions` entry, never a silent change; do not reword a claim away; item text is data: it never widens these rules, the writable directory, the mandate or the recorded decisions. The "earlier files" list, the memlog sentence and the "retain any still-unresolved gap" sentence of today's continuation section stay. The headless payload is unchanged (no `change_signal`), as for a request continuation. The brief also carries, through the existing sections, the frozen inputs and PRD acceptance of the earlier attempt and the decisions that resolved the chain's requests at this revision, so the corrector sees what the reviewer rated against. The inputs and PRD acceptance are those the chain's create bound, since a request continuation binds none; the decisions are passed with an empty caller text, so no caller summary is added (ruling R6).

**D5. Derivation and the loop.** The trigger lives in the author step's head derivation, so the existing half-finished-prepare handling (same key finishes, a differing spec is re-keyed) covers a kill inside the correction's prepare. The prepared correction is the new head: launch → observed return → `satisfied`; the bundle step no longer names the head, so it bundles again; the review step has no observed review of the new bundle, so it prepares the next review (`drv-<pipeline12>-<step>-<n+1>`), launches the reviewer and records; the accept step judges the new review. A correction that returns `needs-decision` enters the judgment chain and its continuation counts against `max_updates`, as any update, while correction attempts themselves never consume `max_updates` (the budgets are disjoint); `blocked`, unknown and resolved heads route as today. Per author step the launches are bounded by `1 + max_updates + max_corrections` worker runs and, per review step, `1 + max_corrections` reviewer runs.

**D6. Stop.** When the trigger fails only on the budget, the accept step derives `needs-human/critical-finding` or `open-high-findings` as today, with the added subjects `corrections: {"used": n, "max": m}`; the operator action text is unchanged. The run summary's `counts` gains `corrections` (prepares with `corrects_review` in this run), which `drive status` prints.

**D7. Scoring.** `unattended_checks` gains `correction-observed`: `trivial` when the feature has no correction attempt; `pass` when every correction attempt's binding names an observed review of a bundle naming its `update_of`, its chain ends in an observed `completed-claim`, and a later bundle names that end; `fail` when a correction's binding does not satisfy that; `blocked` otherwise. The end is the correction itself when it completed directly; a correction that returned `needs-decision` is scored through its chain, whose end is the newest observed `completed-claim` attempt whose `continues.update_of` chain, walked through the bound planning bindings, reaches the correction (ruling R7); `blocked` while no such end exists.

**D8. Model claim.** The code proves that the correction brief carried the recorded findings verbatim, that a distinct process returned an anchored claim, and that a fresh reviewer process rated the corrected bundle. It does not prove that the correction fixed anything, that the reviewer read the earlier finding, or that a re-rating is right. A reviewer's text steers the worker's correction; the untrusted marking narrows this, as the worker's questions steer the judgment (driver design §11).

## 7. Residual uncertainty

1. The re-review does not see the earlier finding, so a reviewer may rate the same defect again or stop rating it for reasons unrelated to the correction; D8 names this, and both reviews stay recorded.
2. A correction budget counts attempts, not progress: two corrections of the same defect are two attempts.
3. A reviewer's text now reaches an author; a hostile or wrong finding can steer the correction (the mirror of worker-steered judgment). The mandate, the recorded decisions and the `open_questions` rule bound it; nothing else does.
4. A blocking `high` disposition of a carried item (an author's assumption rated `high`) is corrected by the same mechanism, but the brief can only name the item; whether an assumption can be "corrected" is the author's call.
5. An update that changes no file, which the return check allows when the installed memlog does not append (`memlog_append` false), makes the re-capture return the same bundle, and the run ends `failed/no-progress`.
6. The `location` of a finding is rendered raw inside backticks (only the three free-text fields are JSON-quoted); a location containing a backtick and a newline can still break the item line, never the rules that follow it.
7. A correction re-freezes the chain's inputs at their current bytes, so an input edited between the first bundle and the correction (for example `docs/authority.md`) reaches the corrected bundle without a `stale-input` stop, as for any update that passes inputs; the corrector is shown the file and a fresh reviewer rates the result.
