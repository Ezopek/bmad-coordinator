# State core usage

The CLI runs from `coordinator/` with Python 3.11 or newer and Git. Python 3.11 is the selected floor; implementation tests ran on Python 3.14, not on every supported version. The validated mutation target is local Linux/ext4. Other platforms and filesystems are refused until tested. Git must support `rev-parse --path-format=absolute --git-common-dir`.

```sh
cd coordinator
python3 -m coordinator_core --help

# Replace this with an existing Git repository on local Linux/ext4.
repo=/absolute/path/to/your/git-repository
token_dir=$(mktemp -d)
token_file="$token_dir/owner.json"

python3 -m coordinator_core --repo "$repo" status
python3 -m coordinator_core --repo "$repo" init
python3 -m coordinator_core --repo "$repo" claim --session manual-demo --token-file "$token_file"
python3 -m coordinator_core --repo "$repo" status
python3 -m coordinator_core --repo "$repo" release --token-file "$token_file"
```

`status` before `init` returns `{"state":"uninitialized"}` without creating state. `init` explicitly creates the database under the Git common directory, shared by linked worktrees. `claim` exclusively creates a private mode-`0600` token file and returns only the owner generation. Keep that file private; later mutations need `--token-file`, and a second owner cannot claim until clean release. Release can be blocked by unresolved assignments. The token file is local ownership material, not a cross-host security boundary.

The general form is `python3 -m coordinator_core --repo PATH COMMAND`; after explicit installation, use `python3 .bmad-coordinator/run.py --repo PATH COMMAND` from the target worktree. Read-only commands include `status`, `doctor --base REF`, `detail KIND ID`, `recover`, `verify`, and `assignment retry ID`; retry reads one JSON object from stdin with `request_fingerprint` and does not launch a worker. `feature add`, `decision add`, `assignment add`/`return`, `bundle capture`, `review add`, `feature revise`, `accept`, and `import` read exactly one JSON object from stdin with their documented model fields; writable commands also take `--token-file` except `init`, `claim`, and validated fresh-clone `import`. `export --token-file PATH --to DIR` writes a versioned checkpoint and handoff. Success emits one JSON object on stdout; errors emit one JSON object on stderr with a stable code and a nonzero exit status. Use `--help` at the relevant command level for the available syntax and `coordinator_core/model.py` for structured input fields.

The installer is a separate explicit step: preview with `python3 coordinator/install.py --repo PATH --preview`, inspect its exact `AGENTS.md` diff and file hashes, then apply with `--apply --preview-sha256 TOKEN`. Commit the resulting package and managed block on the intended base before creating a linked feature worktree. Record the resolved base commit in `FeatureInput.base_commit`; `doctor --base BASE_COMMIT` checks that exact ancestor tree and the current installed bytes without initializing state. `--upgrade` (with `--preview`, then `--apply --preview-sha256 TOKEN`) refreshes an installed package to the source version in place: it requires the installed files and the managed block to be byte-identical to the installed manifest's record (a locally modified file is still `Package collision`), replaces changed files atomically, adds new ones, removes files the new package no longer lists, rewrites the managed block and the manifest, and leaves everything outside the block alone; there is no force path. An upgrade interrupted after its first write leaves a package the installer refuses in both modes (`Package collision` or a changed block); recover it by hand as for a first install: remove the package files and the managed block, then preview and apply again. See [Getting started](getting-started.md#install-the-coordinator-into-a-repository).

The implemented worker commands are `worker run ID --token-file PATH --model MODEL --timeout SECONDS [--client NAME] [--max-turns N]`, `worker inspect ID`, and `worker reconcile ID --token-file PATH`; use the installed wrapper and put `--repo PATH` before `worker`. Run requires a prepared assignment and a current owner. It checks for an existing sidecar, commits the fenced reservation, then creates the sidecar and spawns. Ordinary unresolved prerequisites leave the assignment prepared; a crash after reservation remains an ambiguous attempt and cannot relaunch. Inspect is read-only. Reconcile can bind an already verified terminal receipt but cannot launch or resume work. The terminal receipt digest must already have an owner-fenced database anchor; a crash before that anchor leaves the attempt unknown even if raw output exists. A timeout, ambiguous process state, invalid return, or unexpected file delta also leaves current evidence unknown or blocked for inspection. Inspect and reconcile preserve historical database state while reporting current evidence as unknown on receipt corruption, missing or changed frozen envelope, or file drift. Do not retry the same assignment blindly. A read-only reviewer assignment has no writable paths. The worker adapter report records bounded installed-client results and the completed independent evidence review.

## Worker clients

The worker client is one of a closed registry: `codex-cli` (the default, `codex exec`), `claude-code` (`claude -p`) or `copilot` (`copilot -p`, authors only). `--client NAME` on `worker run`, `bmad run` and `assignment reserve-launch` selects it; without the flag a bound assignment uses its binding's client (`client` in the `bmad prepare` or `bmad review prepare` JSON), else `codex-cli`. A flag that conflicts with the binding, an unknown name, or `--max-turns` for `codex-cli` or `copilot` is `INVALID_INPUT` before reservation. `--max-turns N` applies to `claude-code` only (default 60); it is the client's turn limit (`--max-turns` of `claude -p`: one turn is one model response, however many tool calls it holds, while the result's `num_turns` counts tool rounds; design §7 F19), not the driver's turn count that `drive start`/`drive resume` and `epic start`/`epic resume` take as `--max-turns` (`RunBounds.max_turns`). A pipeline role may set `max_turns` (1–1000, `claude-code` only; design D25): it is part of the pipeline digest, the worker, reviewer and judgment launches pass it, and `launch.json` records it, as `worker run --max-turns` does; without it the default stands. A Claude story attempt (implementation or spec author) whose stream ends with the result `subtype: error_max_turns` (`terminal_reason: max_turns`; observed with no structured output and exit code 1) is recorded `client-stopped` from the client's own result record: a terminal state with an observed receipt (`return.json` with `result: client-stopped`, `client_stop: {kind, num_turns}` with `kind` `max-turns`, no profile payload, an empty `last.json`) under the same scope and integrity checks as a return (a touched protected path or a changed sealed input still ends `unknown`), the fence released, the attempt committed (`[client-stopped]`) and continued by the next attempt (`## Continuation after a client stop`, counted in `max_updates`); a stopped attempt is never verified, bundled or reviewed. `client-stopped` is observed-only: `assignment return` cannot record it, and no other result carries a `client_stop` (`INVALID_INPUT`). Any other profile (a generic or planning author, a code or spec reviewer) and an isolated judgment stay `unknown` at a client stop, with the cause "the client stopped at its turn limit … without a return" in `evidence_needs` (`needs` for an isolated run); every other error subtype stays `unknown`, and a non-zero exit of any client without a stop reports "Worker process exited unsuccessfully" as before. `doctor --base REF --client NAME` adds a `client` object (`name`, `binary`, `version`, `ready`, `reasons`) and folds it into readiness (for `copilot` it also lists the present token variable names and warns when `COPILOT_GITHUB_TOKEN` is absent); like every launch it resolves the binary on `PATH` and runs only `--version`, never a model call. The client is recorded in the binding, the reservation event and both receipts, and replay uses the recorded client's parser. Each attempt runs in a distinct worker process.

Claude Code confinement is **advisory tool policy, not an OS sandbox**; an OS sandbox (a bubblewrap probe) is a follow-up. Authors get `Read,Grep,Glob,Edit,Write,Bash` with `acceptEdits`, under which any tool, including write-capable shell commands such as `touch`, may write inside the worktree except at deny-ruled paths (a shell write there is expected to be denied; unverified, design §13 #7), while writes outside the worktree are denied (the worktree audit is the inventory delta, the sealed-evidence check and the contract digests); denied prompts, `Edit`/`Write`/`MultiEdit`/`NotebookEdit` deny rules for `_bmad/**`, `.agents/**`, `.claude/**`, `.bmad-coordinator/**`, `AGENTS.md` and `CLAUDE.md`, and Bash rules for the exact installed-script prefixes sealed in the binding plus a stdin-only `sha256sum`. A generic (unbound) Claude author gets no Bash rules: Bash stays in `--tools`, and `--permission-prompts none` denies every Bash call that would need approval. A `claude-code` story worker gets `Bash(<argv[0]> *)` for each distinct `argv[0]` of the sealed project `setup` and `verify` commands (implementation drive design D21; operator decision 2026-10-11): it can run the project's commands and, since a test runner executes the code it wrote and `Bash(python3 *)` allows `python3 -c …`, arbitrary code as the operator: writes anywhere, inside and outside the worktree (the Edit/Write deny rules no longer guard the protected paths for it; the sentences above about denied writes outside the worktree and about every rule-named script lying in the sealed contract closure do not hold for it), network access and the inherited, unscrubbed environment (`ANTHROPIC*` and other operator variables, below). The return-time inventory, the scope checks and the contract digests are the audit, and they cover the worktree only; this is the exfiltration surface design §7 F4 names. With `web: true` on a story pipeline's `worker` role (design D23) a Claude story worker also gets `WebFetch` and `WebSearch` in `--tools` and as bare allow rules, and a Codex story worker gets outbound network in its `workspace-write` sandbox (`-c sandbox_workspace_write.network_access=true`, which that sandbox otherwise denies); no receipt records network traffic, the Git delta, the verify receipt, the bundle and the review stay the audit, and the launch receipt records `web: true` so the audit can tell which attempts were granted the web tools (Claude) or the sandbox network (Codex); a Claude story worker reaches the network through D21's Bash rules either way; the reviewer and judgment launches never get it. A Codex or Copilot story worker gets no rule from the project block. A path with a glob or permission-pattern character (`*?[]{},():`) in the worktree, client root or workspace is refused with `INVALID_INPUT` before any rule exists, and so is a `--model` value that starts with `-`. Every script an author rule names lies in the sealed contract closure, so a changed script at return makes the attempt `unknown` with the fence held; a script changed and restored within the run is not detected. Reviewers get no write tools, write-capable Bash denied and every Bash call recorded and audited, with `--add-dir` for the sealed bundle. Some read-only shell commands may be auto-allowed by the client without any rule (`git status`, also piped or chained, in P0/P0r), but not all (attempt 8 denied an author's `git status … | head; git check-ignore …`); the coordinator never relies on it, and neither role's rules limit reads; only a bare `sha256sum` over the sealed paths counts as read evidence. The author deny rules continue the single `--disallowedTools` after `mcp__*`, and every allowed `uv run` prefix carries `--no-project`; uv configuration discovery (`uv.toml`, `pyproject.toml`) is not disabled, so a model-written uv configuration is a limit (design §13 #17). The reviewer rule is one comma-joined `--allowedTools` value, while author rules are separate arguments; the first live smoke (Claude Code 2.1.289, P0 and P0r) observed both forms parsed, one deny rule firing, a ` *` rule matching a bare call and a `>` redirect denied. Env-prefix, `&&` and `$( )` matching stay unverified, and so does whether a shell variable is expanded before matching (attempt 8 allowed an author's `M=<script>; uv run --no-project $M …`; the next P0 checks a non-allowed script in the variable, design §13 #21). These Bash rules are **advisory**: an allowed `uv run` reaches anything the user can, including coordinator state in the Git common directory. The inventory delta and the sealed-evidence check are the audit. The sealed-evidence check detects only modification or deletion of pre-existing sealed evidence (bindings, bundles, ended run receipts, judgments, and the driver's `pipelines/`, `drives/` and `resolutions/`); it does not see reads, network, additions or database writes, so the database relies on owner fencing and anchored receipts. A Claude return is observed only when the retained `stream-json` stream has one init first and one successful result last, both naming the coordinator's preset `--session-id`, an object `structured_output` that the coordinator writes to `last.json` and validates, init tools inside the requested set, and matching init cwd and permission mode when reported. Denials, turns, model ids, reported cost, init facts, MCP isolation gaps and, for a bound review, `bundle_read_basis` (`command` only for bare `sha256sum` over the sealed paths, else `claim`) are recorded as `client_facts`; they are client-reported and never upgrade a claim. Design §5 and §13 record which Claude flags the smoke verified; the auto-updater, background-task and auto-memory variables stay documentation-only. Every worker client runs as the same OS user as the coordinator and inherits the operator's environment, so its own authentication variables are not scrubbed (Claude needs the operator's OAuth or API credentials). A parent agent session's variables never reach `codex-cli` or `copilot`: every inherited `CLAUDE*` and `ANTHROPIC*` variable and the markers `AI_AGENT`, `GIT_EDITOR`, `COREPACK_ENABLE_AUTO_PIN` and `NoDefaultCurrentDirectoryInExePath` are removed, and the run directory's `env-scrub.json` records the names (never values) so a Codex `launch.json` keeps its shape. `env-scrub.json` is an unanchored record, not evidence: no receipt or event carries its digest and it is not sealed while the worker runs, so that worker can rewrite it; Copilot's `launch.json` `isolation` carries the anchored copy of its names. The clients' own auth variables (for example `OPENAI_*`, `GH_TOKEN`) pass. For `claude-code` every inherited `CLAUDE*` variable, including `CLAUDECODE` and a parent session's messaging socket and token, is removed except the documented authentication and provider variables (`CLAUDE_CONFIG_DIR`, the `CLAUDE_CODE_OAUTH_*` tokens, the `CLAUDE_CODE_USE_*` provider switches, the `CLAUDE_CODE_SKIP_*_AUTH` gateway switches and the `CLAUDE_CODE_CLIENT_*` mTLS credentials; `clients.KEEP_ENV`), so environment-based authentication keeps working; the parent-session markers `AI_AGENT`, `GIT_EDITOR`, `COREPACK_ENABLE_AUTO_PIN` and `NoDefaultCurrentDirectoryInExePath` are removed by name; `ANTHROPIC*` and other unprefixed variables pass (including unrelated operator secrets, a documented limit). The launch receipt records the names, never the values, of the inherited `CLAUDE*`/`ANTHROPIC*` variables passed on, of those removed and of those kept. Auto memory is an isolation limit: `--setting-sources ""` did not disable it, the worker now sets the documented `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, and the account-context gate is never `pass`: `fail` if account context is observed, else `blocked (unobserved)`; a probe can only remove auto memory as one route. Claude evidence is Claude-adapter evidence only and is never Codex evidence.

GitHub Copilot CLI (`copilot -p`, client `copilot`) is an **author-only** transport. A read-only assignment, `bmad review prepare` with `"client":"copilot"` and an isolated judgment run are refused with `UNSUPPORTED_CLIENT_MODE` (exit 4) before any reservation or preflight, because returning a result needs write approval and path-scoped write approval is unverified; a Copilot author's work is reviewed by `claude-code` or `codex-cli`. Its confinement is an **advisory approval policy, not a sandbox**: shell commands run with the user's access. Authors get `--available-tools` pinned to a narrowed author tool set (11 of the 21 tools the P0c probe offered; no tool that reaches the network, spawns or drives agents or workflows, or queries past sessions, design §14), `--allow-tool write`, and `--deny-tool 'write(...)'` rules for `_bmad/**`, `.agents/**`, `.claude/**`, `.bmad-coordinator/**`, `AGENTS.md`, `CLAUDE.md` and `.github/**` (the live P0c probe saw `_bmad/**` and `.github/**` denials honoured, C15). Copilot approves a shell command by its bare name, so prefix rules cannot confine `uv`: a bound author instead gets `--allow-tool 'shell(bmad-script)'` plus `shell(sha256sum)`, never `uv`, and the runner writes `RUN/worker-tools/bmad-script` (`0500`, digest in `launch.json` `script_launcher`) and puts its directory first on the worker's `PATH` (recorded as `path_prepend`). The launcher runs under the coordinator's interpreter, isolated and without `site` (`-IS`), and execs the absolute `uv` resolved at launch (recorded) as `uv run --no-config --no-project --python <coordinator interpreter>`, in the worktree. Its environment holds only the `PATH` and `HOME` sealed at launch and `PYTHONDONTWRITEBYTECODE=1`, so no worktree `uv.toml` or `.venv`, no inherited `XDG_*`, `LD_*`, `PYTHON*` or `UV_*` variable and no GitHub token value reaches uv or the script (`launch.json` keeps only the token names). A coordinator interpreter that itself lies under the feature worktree or its common directory (a worktree venv) is refused with `BLOCKED_EVIDENCE` before reservation; after the run the runner seals `launcher-check.json` and treats any change in `RUN/worker-tools` as `unknown` with the fence held. That stdlib launcher runs `uv run --no-config --no-project --python <coordinator interpreter>` only for arguments that start with one bound script form token for token (further arguments only after the full form, never a short option and never repeating or abbreviating one of its options) and otherwise exits 2 without running anything. Some read-only commands, such as `git status` in P0c, may run without any rule; the coordinator never relies on that. The brief and the envelope print the forms by the bare name only, `bmad-script <form> …`. In the second live probe (P0c with the launcher, Copilot 1.0.91) these calls were approved, advisory only:

- the bare-name call, which ran in the worktree, also when piped to `sha256sum`;
- an env-prefixed call: it ran, and a planted `sitecustomize.py` did not;
- a `cd … &&` call: it ran, and the launcher still used the worktree.

These were denied:

- the full-path call, whose identifier is the whole path;
- `uv` itself;
- outside redirects and `touch` chains;
- a launcher call naming an outside script (Copilot's path check).

A script hidden in a shell variable passes Copilot, and the launcher refused it. The pinned tool set was what the model saw, and the prepended `PATH` was visible. An env-prefixed `LD_*` variable still reaches the launcher's interpreter (no OS confinement), and C2 and C8 stay open. Because of the `.github/**` rule, Copilot cannot author work scoped to `.github/`. The only added directory is the run's `worker-return/`. The inventory delta, the sealed-evidence check and the contract digests are the audit; a rewritten allowed script makes the attempt `unknown`. The return is **model-written and coordinator-validated**: the envelope names `return_path`, the model writes one JSON object there (a generic envelope's `instructions` name the exact path; a bound planning brief says so too). Copilot has no schema flag, so the envelope (and a bound brief) lists every required key with its type, the profile extras and a JSON skeleton, rendered from the same schema object the run writes to `return.schema.json` and `_final` enforces (the second live attempt's S1 omitted `checks` and `descendants`), and the runner accepts only `worker-return/return.json` as the sole entry (regular, single link, at most 1 MB, nesting at most 64) before `_final` and the profile check; the final assistant message is never read. That is weaker than Codex or Claude schema enforcement. Freshness rests on a coordinator-generated `--session-id` in a fresh per-run `COPILOT_HOME` (a duplicate id silently resumes): after the run the session folders, Copilot's `.session-operation-locks/` listing (it must hold only `<id>.lock`; any other extra entry is `unknown`), `workspace.yaml` (`cwd`, `created_at`) and the absence of a `$HOME/.copilot` session are sealed once in `freshness.json`, and replay reads only that seal. A return is observed only when the retained JSONL stream ends in one `result` record with `exitCode` 0 and the preset `sessionId`, with no `session.error`. Tool-start events, when present, must name their tool, stay inside that narrowed author tool set (any other tool, and any offered tool a `session.usage_checkpoint` lists outside it, is `unknown`), and include a start of an edit-category tool (`create`, `edit`, `str_replace_editor`, `apply_patch`, read from the bundled 1.0.91 tool table) naming `return_path`, or a `bash` start whose command writes that exact path as the target of `>`, `>>`, `>|`, `&>` or `tee` (a shell redirect, which Copilot approved into the added directory without a rule in the third live attempt). A start whose own completion was denied, or that has no `toolCallId`, never counts. The basis is sealed as `return_write_basis` (`tool` or `shell`). The envelope and brief ask for the file-creation tool and call a redirect accepted but discouraged. A `view`, a read, `cp` or `mv`, a `$VAR` path or a bare mention of the path in a comment or heredoc body does not count (a write-shaped text there still does). Copilot receipts sealed before this rule replay `unknown`; re-run them; without tool events `tool_check` is `blocked`, never passed. MCP servers (except those reported `disabled`), hooks and subagents are isolation gaps, and every terminal refusal names its specific cause in the evidence needs; usage, `copilotVersion` and denials are client facts. A denial is a `tool.execution_complete` record whose `error.code` is `denied` (the only denial record P0c saw in stdout), named by its start's tool; a denied `permission.completed` still counts when present. The worktree's `.agents/skills` load as Copilot project skills despite `--no-custom-instructions`, so `launch.json` `isolation.gaps` records `project-skills:.agents/skills` when that tree exists. `--model` is required with no coordinator default and is recorded; it must name a model the account can use (an unavailable one exits 1 with no `result`, which consumes the attempt as `unknown`; P0c's account default was `claude-sonnet-5`). The auth source of a clean per-run home is still unknown (C2). The worker sets `COPILOT_AUTO_UPDATE=false` and removes inherited `COPILOT*` variables except `COPILOT_GITHUB_TOKEN`; `GH_TOKEN` and `GITHUB_TOKEN` pass; names only are recorded. Copilot has no max-turns or timeout flag, so the coordinator timeout applies. Its transport has two live probes (P0c, Copilot CLI 1.0.91) and no observed coordinator-run author yet (the one S1 attempt ended `unknown` on the missing return keys); the coordinator logic is tested with a fake `copilot`, and the flags that probe did not exercise stay help- or docs-only (design §14). Copilot evidence is Copilot-adapter evidence only and is never Codex or Claude evidence.

SQLite is the canonical local coordinator state; BMAD files remain authoritative for their content. Every domain change marks export pending. Export and import validate checkpoint content and revision, but importing a fresh clone does not restore ownership, launcher identity, or current acceptance. Direct CLI return and review evidence is **reported**; the Python launch-evidence seam has the same default. The receipt adapter can mark only a validated launch/return **observed**; generic worker review classification stays **reported**. Only `bmad review record` can record an **observed** review (see below). A claimed check, denied write, or descendant state is not proof without event and filesystem/process evidence. A reported review cannot authorize acceptance. There is no automatic takeover or proof that an external writer stopped. `recover` and `verify` expose uncertainty instead of treating missing evidence as success.

`verify` preserves historical acceptance separately from its current validity. A later open critical review for an accepted bundle reports `unknown` with reason `open-critical-finding`; the history remains intact. Inspect the per-acceptance `checked` entries: the aggregate can be `current` when another accepted bundle is still current.

## BMAD planning and review

Every planning brief, for every client, states the return contract the profile check enforces (`bmad_planning.RETURN_RULES`, in the check's own refusal words): the status-to-result mapping, `complete` only without open questions, the exact canonical `unresolved_question` with `options: []`, the create and update delta rules, `affected_ids` holding only assignment ids of this feature (usually `[]`; review briefs state it too), and the two path refusals (an artifact or memlog path with an unresolved `{...}` placeholder, or one that is not the bound workspace path). Claude reviewer briefs add that any shell command other than a bare `sha256sum` over sealed paths makes `bundle_read` a claim.

The `bmad` commands are thin wrappers over the core. Every gate also runs in the plain paths: `assignment reserve-launch`, `worker run`, `bundle capture`, `accept` and `verify` apply the same checks to bound assignments and bundles; generic unbound work is unchanged. Put `--repo PATH` first; owner-fenced commands take `--token-file PATH`; stdin is one JSON object.

| Command | Input | Output |
| --- | --- | --- |
| `bmad discover [--client-root R]` | none | contract report with capabilities, limitations, `fingerprint_sha256` |
| `bmad prepare` / `bmad run ID --model M --timeout S [--client C] [--max-turns N]` / `bmad status ID` | `PlanningPrepare` fields (`coordinator_core/bmad_planning.py`), including `client` | bound planning assignment, run report, verdict view |
| `bmad bundle` | `{feature_id, workspace, dependency_paths?}` | `{id, artifact_paths, dependency_paths, source_assignment_ids}` |
| `bmad review prepare` | `{bundle_id, reviewer_id, key, compat_decision_id?, lenses?, client_root?, client?}` (`compat_decision_id` required for a planning bundle, refused for a commit-bound one; design D22) | `{assignment_id, brief_ref, binding_sha256}` |
| `bmad review record ID` | none | `{id, provenance_class, critical_open}` |
| `bmad accept` | `{bundle_id, review_id}` | `{id, open_high_findings}` (JSON pointers into the review, listed, never blocking) |
| `bmad verify` | none (read-only) | core verify plus `reasons` per acceptance |

Record a compatibility judgment for a discovered fingerprint with `decision add`: `source_kind: "coordinator"`, `source_ref: "bmad-fingerprint:<sha>"`, `choice: {"bmad_compat": "<sha>"}` at the current mandate revision. It records who judged which hash; the code cannot check that the judgment is right.

- **Input roles.** `bmad prepare` accepts only the roles `driving-brief`, `authority` and `accepted-prd`; any other role is `INVALID_INPUT`. `prd_acceptance` sets `accepted-prd` on the accepted PRD files. `authority` and `accepted-prd` inputs and the parent spine are required dependencies; `driving-brief` inputs are not.
- **Bundle.** Artifacts are the files under `workspace` claimed by observed returns of the feature. A claimed file that is missing, or whose bytes match no observed claim, is refused (`BLOCKED_EVIDENCE` naming the path), and so is a workspace file a contributor was given as a source but no observed return claimed. Files nobody claimed and no contributor was given are not part of the bundle. Contributors are all assignments whose returns touched the artifacts, including partial and correction history. Required dependencies are added automatically at the bytes frozen for each contributor; when a later observed completed contributor in the same `update_of` chain re-froze a path, its digest replaces the earlier one. Plain `bundle capture` refuses a bundle that omits a required dependency or carries other bytes for it (also when the path is bundled as an artifact, e.g. a parent-folder bundle), a customization mismatch, a stale or tampered contributor receipt, and mixed bound/unbound contributors. A `dependency_paths` entry inside the workspace is `INVALID_INPUT`: workspace files are artifacts. `prd_acceptance` must name a current acceptance of bound `bmad-prd` work that includes each contributor's PRD file.
- **Sealed decisions.** A bundle seals, by id and row digest, every decision that resolved a contributor's decision request (the continuation chain) and every decision a contributor was prepared with through `bmad prepare` `decisions` (recorded as `{id, digest}` in its binding; a row changed since prepare makes capture `STALE_INPUT`), including the decisions sealed in an accepted PRD bundle that an architecture contributor consumes through `prd_acceptance` or an `accepted-prd` input at the accepted bytes; the review brief lists those under "Inherited decisions" with the accepted bundle id, and so does the consuming author's brief (stored rows and provenance only, never caller text; no section when nothing is inherited). Only matching accepted bundles are opened; one whose contributor binding cannot be read is matched by its sealed manifest instead, and if that manifest cannot be read either, `bmad prepare` is refused (`UNKNOWN_EVIDENCE`). The key is absent when there is none. A sealed decision row that later changes makes `verify` report `stale` (reason `decision-record`) and review prepare `STALE_INPUT`; a missing row is `unknown`.
- **Review prepare.** It refuses (`BLOCKED_EVIDENCE`) while another attempt may be running in the worktree, as `bmad prepare` does, because a new brief would join that attempt's file delta. Before any process exists, this checks the sealed copy, the live bundle bytes and, for a planning bundle, the contract fingerprint (a commit-bound bundle's review runs no discover and seals no contract, design D22). It writes the immutable brief: sealed paths, lenses (default `adversarial`, `edge-case-hunter`), severity rubric (a finding that contradicts a mandate clause, or makes an artifact's output invalid under a standard the mandate requires, is `critical` and cites the clause id; a `critical` disposition of a carried item sets `critical_open` like a critical finding; severity stays a reviewer claim), every carried contributor assumption and partial marker, the sealed decisions rendered from their stored rows (recorded facts to check the artifacts against, never caller text), and a profile line with the exact `bundle_id`, `manifest_digest`, sealed root and lenses the return must echo. Then it binds a read-only `bmad-review-v1` assignment. It is idempotent on `key`. Launch with `bmad run` or `worker run`.
- **Review record.** This builds the review from the anchored return receipt. The caller supplies no finding, provenance or `critical_open`. The same receipt never yields a second review: a retry after a crash returns the stored one while the live bundle bytes are unchanged; after a change the retry is `STALE_INPUT` and the stored review remains.
- **Codes.** Contract drift or changed live bundle bytes since binding: `STALE_INPUT`. A missing compatibility decision, an unbound or non-independent reviewer, a reused contributor thread, a blocked or undecided reviewer, or an open critical finding: `BLOCKED_EVIDENCE`. A forged or edited receipt or sealed copy: `UNKNOWN_EVIDENCE` at review prepare or record; at `accept` it is a gate reason (`BLOCKED_EVIDENCE`) and `verify` reports `unknown`. Unsupported installed contract: `UNSUPPORTED_CONTRACT` (exit 4).

Evidence limits: an **observed** review means only these things. A distinct worker process returned an anchored structured result that validates. Its whole source id (client and thread) differs from every contributor's, and its reviewer label is not a contributor author. Its return matches the sealed bundle, lenses and carried items exactly. `critical_open` is derived from the anchored findings and dispositions; a lower caller value is refused. Reading, understanding, per-file digest attestations, lens text and findings are **model claims**. No command-event parser is used as proof. Generic `review add` stays `reported`. An imported checkpoint has no sidecars, so its bound reviews and acceptances are `unknown`. A reported critical finding still blocks acceptance. `accept` and `verify` check the bundle files, contract fingerprint, frozen dependencies, mandate, compatibility decision and historical receipts of the reviewer and every contributor. Unrelated later worktree edits or commits do not retire an acceptance. All tests use fake `codex` and `claude` executables; this slice has no live BMAD, Codex or Claude evidence yet.

## Unattended driver

`drive` is an explicitly started, bounded, foreground process that takes ownership of one feature by orderly handoff and runs its sealed pipeline turn by turn: reconcile, derive, at most one action, record ([design](unattended-driver-design.md)). It answers a worker question only through a model-backed coordinator judgment that cites, for every answer, a delegated authority clause, and otherwise stops with `needs-human`. **Status: implemented and tested with fake clients on this host; the live hook has run with real Claude Code workers (see below), but no live run has reached `done`.** Put `--repo PATH` first, as for every command.

| Command | Mode |
| --- | --- |
| `drive start --feature F --pipeline FILE --token-file T [--max-turns N] [--deadline S] [--human-wait S] [--judgment-root DIR]` | Claims ownership as session `drive:<lease-id>`, binds the pipeline, runs, prints the summary. Defaults: 20 turns (the driver's own turns, `RunBounds.max_turns`; a role's `max_turns` is the client's turn limit, [Worker clients](#worker-clients)), 7200 s, no human wait. `--judgment-root` (an ext4 directory outside the target repository) is required when `max_judgments > 0`. |
| `drive resume --token-file T [--max-turns N] [--deadline S] [--human-wait S] [--judgment-root DIR]` | A new run of the owner session's lease; bounds default to the lease's start bounds, and a different judgment root is refused (`judgment-root-mismatch`). |
| `drive status [--feature F]` | Read-only, creates nothing: lock holders from `/proc/locks`, leases and their last run (`ended`, `end_event`, outcome, reason, intervention count, `corrections`), derived steps, the inbox, open requests and windows. |
| `inbox add decision` / `inbox add stop` | stdin `{feature_id, request_id, choice, reason, source_ref[, mandate_revision]}` or `{feature_id, reason, source_ref}`; no token; writes one private immutable file. |
| `inbox list [--feature F]` | Read-only: every message as `pending`, `consumed` or `rejected` with its reason. |
| `attempt resolve ID --confirm-unknown --token-file T` | Operator only; stdin `{reason, source_ref}`; holds the shared lock. |

The deadline must be at least the largest role timeout plus 120 s (`bounds-insufficient`). Every owner-fenced command holds a shared lock on `<common-dir>/coordinator/drive.lock` and the driver an exclusive one, so a running driver and a fenced command refuse each other with `OWNERSHIP_CONFLICT` (exit 3).

**Pipeline.** One JSON object, sealed by content hash and anchored at bind; step state is derived from rows and receipts, never stored:

- **Kinds.** The set is closed: `compat` (exactly one, first; the compatibility decision stays attended), `author` (`bmad-prd` or feature-altitude `bmad-architecture`, intent `create`; its question, judgment, decision and update chain is internal, bounded by `max_updates` and `max_judgments`, and its correction attempts after a blocking review by the optional `max_corrections`), and the slice-3 wrappers `bundle` (`of` an author step), `review` (`of` a bundle step, `reviewer_id` distinct from every author of the pipeline, a `reviewer` role whose client has a write-free read-only mode), `accept` (`of` a review step) and `export` (last; `to` an existing, normalized absolute directory on local ext4 outside every feature writable scope). `prd_from` names an accept step of `bmad-prd` work and becomes the architecture prepare's `prd_acceptance`. A story pipeline adds `setup`, `implement`, `commit`, `verify` and `status`, has no `compat` step (design D22) and its `bundle` takes a `verify` step ([Story drive](#story-drive)).
- **Refusals** write nothing. `UNSUPPORTED_STEP` (exit 4): an unknown kind, skill, intent or client, a reviewer or judgment client without a write-free read-only mode (for example the author-only `copilot`), a skill or intent on a wrapper step, `max_judgments > 0` without the mandate list `authority.delegated: [{id, text}]`, and everything outside the slice (epics, sprint status, Loop, `bmad-spec`, `bmad-ux`, `validate`, `intent: update`, branches). `INVALID_INPUT` (exit 2): shape, types, references, budgets, an export directory that is missing or inside a writable scope. `UNSUPPORTED_FILESYSTEM` (exit 2): an export directory not on local ext4 (for example tmpfs `/tmp`). Another pipeline at the same mandate revision: `IDEMPOTENCY_CONFLICT`.
- **Derivation.** A bundle step is satisfied by a bundle of the author's workspace that names its head; a review step by a recorded observed review of that bundle (otherwise prepare, launch the `reviewer` role, or record its observed completed return); an accept step by an acceptance of the bundle that `verify` reports current; an export step when the export pointer is at or after the feature's last *domain* event and its directory exists under `to`. Driver, judgment, inbox and owner events never make an export stale; a later domain event publishes a new `checkpoint-r<rev>-<digest>` directory, and a published one is never overwritten. Wrapper calls run the same slice-3 gates as the attended `bmad` commands; a gate error, and any exporter error at the export step, ends the run `needs-human` with the gate code.
- **Review outcomes.** Medium and low findings do not block acceptance. An open critical finding ends the run `needs-human/critical-finding` with the review id and no acceptance; the author step first prepares up to `budgets.max_corrections` (optional, default `0`) correction updates that carry the blocking findings from the recorded review, each re-bundled and re-reviewed; the stop carries `corrections: {used, max}` and the summary `counts.corrections` ([correction-round design](correction-round-design.md)). An open `high` finding (a review finding, which carries no disposition, or a carried item disposed at `high`) ends the run `needs-human/open-high-findings` with `finding_ids` (JSON pointers such as `/findings/0` into the recorded review) and no acceptance, unless the pipeline sets the optional top-level `"accept_on_high": true` (default `false`; sealed with the pipeline and recorded in the lease). Both stops' subjects also carry `finding_counts`, the counts of the review they name (design D26, [Story drive](#story-drive)). Then either accept attended with the driver's token while no driver runs (`bmad accept` keeps the critical-only rule and lists the review's `open_high_findings` in its result) and `drive resume`, which finds the acceptance; or `release`, correct and re-review attended, then `drive start`. An acceptance that turns stale ends the run `needs-human/acceptance-stale` and is never redone.

**Bounded restarts.** This snippet is the documented `drive-loop` (extracted verbatim by the tests). It is a bounded shell function, not supervision: it restarts on exit 10 (`continue`) and after a death by signal (exit above 128) only while `drive status` shows the last run without `drive.ended` or `drive.stop-acknowledged`; it stops on any other exit and once N restarts are used. It needs `python3` to read the status JSON.

```sh
# drive-loop: begin
# drive_loop --max-restarts N COMMAND [ARG...]
# COMMAND is called with one more argument: `start` (the first run: drive start ...), `resume`
# (drive resume --token-file T) or `status` (drive status --feature F, read only).
drive_loop() {
  if [ "$#" -lt 3 ] || [ "$1" != --max-restarts ]; then
    echo 'usage: drive_loop --max-restarts N COMMAND [ARG...]' >&2
    return 2
  fi
  case $2 in ''|*[!0-9]*) echo 'drive_loop: N must be a non-negative integer' >&2; return 2 ;; esac
  dl_max=$2 dl_restarts=0 dl_verb=start
  shift 2
  while :; do
    "$@" "$dl_verb"
    dl_code=$?
    if [ "$dl_code" -eq 10 ]; then
      :
    elif [ "$dl_code" -gt 128 ] && "$@" status | python3 -c 'import json, sys
leases = json.load(sys.stdin).get("leases") or []
last = leases[-1].get("last_run") if leases else None
sys.exit(0 if last and not last.get("ended") else 1)'; then
      :
    else
      return "$dl_code"
    fi
    if [ "$dl_restarts" -ge "$dl_max" ]; then
      echo "drive_loop: stopping after $dl_restarts restarts (exit $dl_code)" >&2
      return "$dl_code"
    fi
    dl_restarts=$((dl_restarts + 1))
    echo "drive_loop: restart $dl_restarts of $dl_max after exit $dl_code" >&2
    dl_verb=resume
  done
}
# drive-loop: end
```

```sh
drive_cmd() {
  case $1 in
    start) run drive start --feature "$feature" --pipeline pipeline.json --token-file drive.json \
             --judgment-root /ext4/scratch/judgments --max-turns 60 ;;
    resume) run drive resume --token-file drive.json ;;
    status) run drive status --feature "$feature" ;;
  esac
}
drive_loop --max-restarts 3 drive_cmd
```

**Exits.** `done` 0 (every step satisfied, the export current, ownership released if D2 holds), `continue` 10 (`max-turns` or `deadline`), `needs-human` 11, `failed` 12 (`ownership-lost`, `no-progress`, `corrupt-state`, `internal-error`). Pre-run refusals keep exits 2 to 5 and write nothing: `run-unbound`, `bounds-insufficient`, `judgment-root-required`, `judgment-root-mismatch`. The `needs-human` reasons are closed: `question-refused`, `question-conflict`, `judgment-budget`, `judgment-unknown`, `judgment-preflight`, `update-budget`, `attempt-unknown`, `attempt-resolved`, `fenced-by-other`, `unobserved-return`, `worker-blocked`, `reviewer-blocked`, `compat-missing`, `compat-review`, `contract-drift`, `critical-finding`, `open-high-findings`, `acceptance-stale`, `stale-input`, `mandate-revised`, `operator-stop`, `signal-stop`, `signal-abort`; a story pipeline adds `product-decision`, `verify-env`, `worktree-drift`, `status-shape` and `correction-budget` ([Story drive](#story-drive)). A first Ctrl-C stops gracefully at the next turn boundary; a second one, SIGTERM or SIGHUP aborts the running attempt (it stays unknown with the fence held).

**Inbox.** Answers and stops are private immutable files under `<common-dir>/coordinator/inbox/`, consumed by the owner only at turn boundaries and during `--human-wait`. A decision written inside an attempt or judgment window is rejected (`written-during-attempt`); re-send it once `drive status` shows the window closed. Stops are exempt and stay pending until acknowledged. An operator answer preempts an unused judgment; to override a recorded decision, stop, release and decide attended.

**Stranded attempts.** A kill during an attempt leaves it unknown with the fence held, and the driver never relaunches it. A Claude story attempt stopped at its turn limit is not stranded: it ends `client-stopped` (design D25, [Worker clients](#worker-clients)), and the driver commits and continues it. Only the operator frees it: `attempt resolve ID --confirm-unknown --token-file drive.json` with stdin `{reason, source_ref}`, while no driver runs. It refuses a non-holder, an attempt whose pid was never recorded (that window strands the worktree permanently), and a process that may still live (the recorded pid with the same start time on the same boot, or any `/proc/*/cmdline` holding the launch token). It seals the evidence, records an `operator-reported` decision and moves the attempt to `resolved-unknown`. **Cost:** the fence is released on operator evidence only; an unobserved descendant may still write, and the files it left stay unclaimed and are never bundled as observed work. Then `bmad prepare` a new create or update for the step (or revise the mandate) and `drive resume`.

**Evidence and limits.** The summary (`drives/<lease>/<run>/summary.json`, anchored by `drive.ended` or `drive.stop-acknowledged`) records the outcome, typed `interventions` (`inbox-decision`, `inbox-stop`, `signal`, `attempt-resolve`, `attended-generation`, `resume-after-needs-human`), `restarts`, counts and every judgment-backed decision with its authority id, key and receipt. "Proved unattended" means only the two fake-client tests on this host (`test_proved_unattended_run_operator_absent` and its kill-and-restart twin): production registry entries, fake binaries on `PATH`, a real child driver, zero interventions. In the run without a restart, `unattended_checks` scores `no-duplicate-after-restart` as `trivial`, never `pass`; `correction-observed` is `trivial` in a run that no review blocked. It does not show live client behavior, Claude Code support, overnight operation or liveness (there is no supervisor). A judgment's correctness is a model claim, and a worker can try to steer its own judgment through its question text; the untrusted-data marking, the authority id and the 24-character verbatim quote narrow this but do not remove it. Likewise a reviewer's recorded finding text can steer a correction ([correction-round design](correction-round-design.md) D8, §7.3): the brief marks it as the reviewer's claims, not decisions, and JSON-quotes it (the `location` locator stays a backticked raw string); the mandate, the recorded decisions and the `open_questions` rule bound it, nothing else does. Inbox files are trusted as the same OS user.

```json
  {"id": "impl-review", "kind": "review", "of": "impl-bundle", "reviewer_id": "code-reviewer"},
  {"id": "impl-accept", "kind": "accept", "of": "impl-review"},
  {"id": "finish", "kind": "status", "phase": "done", "of": "impl-accept"}]}
```

- **Steps.** A story pipeline runs, in this order, `setup` (one), `status` `phase: start` (no `of`), `implement` (one; `author_id`, `story: {spec_path, story_key}`, which must name the feature's story, else `STALE_INPUT` at bind), `commit` (`of` the implement step), `verify` (`of` the commit step), `bundle` (`of` the verify step), `review` (`reviewer_id` distinct from the author; the code lenses `acceptance`, `matrix`, `scope`, `security`, `regression` are fixed), `accept` and `status` `phase: done` (`of` the accept step), then an optional `export`. A `compat` step is refused (`INVALID_INPUT`, design D22), so a story pipeline bound before D22 no longer loads: `drive resume` refuses it (bind a new pipeline without it at a new mandate revision) and `drive status` lists that feature with `steps: []`, `pipeline_sha256: null` and an `error` `{code, message}` instead of its steps (the same entry reports any other pipeline that fails to load, for example a tampered sealed file: the code says which). Planning author steps and an `implement` step never mix (`INVALID_INPUT`).
- **Project.** `setup` and `verify` list commands `{name, argv, timeout_seconds, cwd?}` (distinct short names), run without a shell, each under its own timeout, in the story worktree; `verify` needs at least one command, `setup` may be empty. An `argv` element `{changed_files}` expands to the attempt commit's changed files that still exist (a name starting with `-` is passed as `./<name>`, never as an option); with none, the command is `skipped`. An element containing `{main_worktree}` names the repository's main worktree in its place (the parent of the common `.git` directory; design §7 F6: a `setup` command links a dependency directory of the main checkout into the story worktree); without one (a bare common directory) the command is `skipped`. `env` names the variables copied beside `PATH`, `HOME`, `LANG` and `LC_ALL`; `commit_identity` (non-empty name and email) authors every coordinator commit; `output_limit_bytes` (1024 to 16 MiB) bounds the captured output and the inline diff; optional `rules` lists relative files the worker reads first; optional `artifacts_dir` (default `_bmad-output/implementation-artifacts`, a normalized relative POSIX directory without glob characters) holds `sprint-status.yaml` and `deferred-work.md`, and a writable scope covering it is refused at prepare; optional `briefs_dir` (default `_bmad-output/coordinator/briefs`, the same grammar, never under `.git/` or `.bmad-coordinator/`) holds the story and code review briefs, a writable scope covering it is refused at prepare (`UNSAFE_PATH`) and a worker write into it at return (design D22). The block is sealed with the pipeline and is part of its digest: changing it means a pipeline bound to a new mandate revision. `max_corrections` has no story default: absent means `0`, as for planning, so set it explicitly (the example uses 3); it is shared by verify and review corrections (a spec chain counts its own corrections separately) and capped at 6 for a story pipeline (a planning pipeline keeps 4). The setup step first records `git --version` and needs Git 2.40 or later (the commit stat reads no in-tree attributes through `GIT_ATTR_SOURCE`); an older Git stops `verify-env` before any command runs.
- **Facts.** Every attempt is committed by the coordinator (`story(<key>): attempt <n> [<result>]` with the result `completed`, `needs-decision`, `blocked` or `client-stopped`, trailer `Coordinator-Assignment`), with `--no-verify`, hooks and signing off, and never squashed; an attempt that changed nothing is recorded `empty` without a commit, except a `completed` attempt whose HEAD already is an attempt commit of this story: it stands on that commit (`stands_on` in its record, the record and patch copied) and is verified, bundled and reviewed there under its own assignment id (design D9 and D11, F2), so a worker that writes first and asks second, or a correction whose answer the code already satisfies, reaches the gate. Every story prepare carries the chain's resolving decisions (`decisions` in the binding, *Recorded decisions* in the brief, the bundle manifest and the code review brief; design D21, F3). A worker return that touches a protected path is refused, and so is one that adds or edits a `.gitignore` or `.gitattributes` at any depth (one Git does not ignore: Git-ignored files in the scopes stay invisible to every gate, design §7). Every coordinator Git step (commit, verify, bundle, status) and the acceptance's currency need HEAD on the story branch. The verify commands run on that commit with a sealed receipt; the bundle names the commit and needs the writable scopes clean against it; an acceptance is current only while the newest verify record of the bundle commit passed; the status files are committed by the coordinator with the trailer `Coordinator-Status` (spec and story `in-progress` at start; `done`, the spec's `## Coordinator Result` section and the `deferred-work.md` entries at done). Receipts live under `<common-dir>/coordinator/story/<feature>/`. The summary's `counts.commits` and `counts.verifications` count this run's commit and verify turns (an empty attempt's record included) and `counts.corrections` covers verify and review corrections; the steps of `drive status` carry the story subjects (commit sha, verify outcome, status sha).
- **Questions.** A worker asks one question per `needs-decision`, with `options`; a condition it cannot change is a question whose text starts with `BLOCKED:`. A return with several questions is re-asked without a judgment (a `coordinator` decision with `source_ref` `driver:form`, counted in `max_updates`). An attempt that returns `completed` without a change gets one continuation; a second one stops `worker-blocked` ("no change produced"). An attempt the client stopped at its turn limit (design D25) is committed and gets a continuation as an empty `completed` attempt does (`continues_stop`; the binding's `continues` is `{update_of, request: null, client_stop: true}`; counted in `max_updates`), and so does each later stop while the budget lasts; it is never verified, bundled or reviewed, and with `max_updates` spent the run stops `update-budget` (the subjects carry `client_stop`). A continuation after a decision that follows a correction (its chain leads back, through request continuations only, to a review or verify correction) repeats that correction's items after the decision lines, and the binding's `continues` records it as `after_correction`; it counts in `max_updates`, never as a correction (design D26).
- **Judgment v3.** Implementation and spec requests are judged under `coordinator-judgment-v3`: `verdict` `defer` with a `deferred` list records a reversible choice as a `coordinator` decision whose `source_ref` starts `mandate:r<rev>:deferred` and becomes a `deferred-work.md` entry at `done`, dated by the judgment's sealed `classified_at`. A binding question (persisted data, external contracts, security, user-visible behaviour beyond the Intent, deleting or renaming public things, new dependencies, a choice a later code change cannot undo) or an uncertain one is refused, and the run stops `product-decision` (`spec-decisions` for a spec author's request). Planning requests keep v2.
- **Spec from the epic (design D24).** A story added from its epics entry runs a spec chain before `setup`: `spec` (the first step; `author_id`, `story: {spec_path, story_key}`; only for a story added from an epic, which needs one, else `STALE_INPUT` at bind), `bundle` (`of` the spec step), `review` (the spec lenses `readiness`, `scope`, `verification`, `edges`, `fidelity` are fixed), `accept`, and `status` `phase: spec` (`of` that accept); a `setup` before that status step is refused. The spec author (profile `bmad-spec-author-v1`, role `spec-author`, the worker role's client, no commands) writes only the spec file from a coordinator brief: the epics entry verbatim, its preconditions, the files of the optional `project.context` list (relative files read first, for example a PRD, the architecture or an epic context), the `done` specs of the same epic, `project.rules` and the spec template with the pipeline's `verify` commands as its Verification section. The brief also lists the story's code scopes: a change the story needs outside them is an Open Question, never a task, and the spec review's `scope` lens marks such a task `high` (design §7 F9). It investigates the repository first and asks only about intent gaps, as `## Open Questions` entries `- Q<n>: <question> — options: <label> (<consequence>) / … — recommendation: <label>`: the return's `open_questions` must equal them (else `unknown`), several questions make one `needs-decision` return (the one-question rule is for implement attempts), and a `completed` return that wrote the spec needs its status `ready-for-dev` and no Open Questions section. The questions are judged under v3 like an implement attempt's: an answer or a deferral under a clause continues the author, a refused one stops `spec-decisions`. **The accept is the operator's by default:** the reviewed spec stops `spec-decisions` with `questions: []`, its digest and the `S` clauses the carry will delegate (also after answered questions), because the spec's frozen section becomes the story's delegated authority; the operator accepts it, or sends it back with a `decision add` whose `source_ref` is `spec-revise:<bundle_id>` and whose `choice` is `{"revise": <the changes>}`, and the author then revises the spec in an update counted in `max_updates` and the revised spec stops for the accept again. The pipeline's `spec_auto_accept: true` lets the driver accept instead. An empty `completed` spec attempt stops `worker-blocked`. The digest renders the frozen section: the Intent problem and approach, each matrix row as `when <input>, then <expected>`, the Always and the Never lists. The `spec` status step refuses a spec whose bytes differ from the accepted commit (`worktree-drift`), then flips its frontmatter and the sprint-status key to `ready-for-dev` and commits `story(<key>): spec ready-for-dev` (trailer `Coordinator-Status`, the `story.status` record `spec`). In the same run the driver **carries** the story to the spec: a `coordinator` decision `spec-ready:<sha>`, the mandate revised from the spec at that commit exactly as `story add` reads a hand-written spec (the `S` clauses, then the `P` clauses), the same pipeline bound at the new revision and the lease re-sealed (a second `drive.leased` record of the lease id, `carried_from` the old digest); `counts.carries` counts it, and a run killed inside the carry finishes it on resume instead of stopping `mandate-revised`. At the new revision the spec chain is satisfied by the `spec` status receipt while its commit is on the story branch (off the branch the run stops `worktree-drift`), and the setup baseline and the start status commit sit on that commit instead of the base commit.
- **Stops** (each with `operator_action`; below in the driver's words, `<driver token>` as printed and `…` for a subject). Story pipelines add `product-decision`, `spec-decisions`, `verify-env`, `worktree-drift`, `status-shape` and `correction-budget` to the closed `needs-human` list; `question-conflict`, `judgment-budget`, `update-budget`, `critical-finding` and `open-high-findings` keep their planning actions (the subjects of `critical-finding` and `open-high-findings` carry `finding_counts`, `{critical, high, medium, low}` over the named review's findings and dispositions, design D26; `detail review` prints the same `finding_counts`), and `worker-blocked` gets the story action below. A stalled or killed attempt still ends `attempt-unknown` and needs `attempt resolve`.

| Reason | When | `operator_action` |
| --- | --- | --- |
| `verify-env` | red setup or baseline, or Git older than 2.40; nothing launched; the run ends | "fix the environment so the setup and baseline commands pass (failed: …), then drive resume (setup and baseline are re-run); changing the commands needs a pipeline bound to a new mandate revision: release --token-file \<driver token\> first" |
| `worktree-drift` | HEAD moved under the driver or left the story branch at commit, verify, bundle or status, or the writable scopes changed after the attempt commit (bundle) | "restore the story branch: inspect it (HEAD is expected on the story branch at …; the detail says what differs), switch back to the story branch if HEAD left it, run `git reset --mixed …` if HEAD moved (a mixed reset keeps the working tree; a hard reset destroys the worker's uncommitted attempt) and remove stray changes in the writable scopes after an attempt commit, then drive resume; or release --token-file \<driver token\> and finish the story attended" |
| `status-shape` | a status file the coordinator cannot edit; the detail names the line, every file is left unchanged | "fix the project status file (…) in the story worktree without committing it, then drive resume (the status step edits and commits it); or release --token-file \<driver token\> and finish the story attended" |
| `correction-budget` | red verify with `max_corrections` spent | "the red verify receipt of the attempt commit is final, so a plain drive resume stops here again: fix the failing verification by hand in the story worktree and commit nothing yourself; then with the driver's token while no driver runs, revise the mandate, release --token-file \<driver token\>, then drive start a pipeline bound to the new revision (its corrections count starts at zero; raise max_corrections there if needed): the coordinator commits the writable scopes, so the next attempt's commit takes your fix; or release --token-file \<driver token\> and finish the story attended" |
| `worker-blocked` | a `blocked` return, or a second empty `completed` attempt | "the attempt of assignment … is final (…), so a plain drive resume stops here again: fix the condition in the story worktree or the brief inputs; then with the driver's token while no driver runs, revise the mandate, release --token-file \<driver token\>, then drive start a pipeline bound to the new revision (its first attempt is a fresh create); or release --token-file \<driver token\> and finish the story attended" |
| `product-decision` | a binding or uncertain question outside every clause; the subjects carry the question, the options and the refusal | "inbox add decision for request …, then drive resume (or keep a driver waiting with --human-wait)" |

`worker-blocked` and `correction-budget` are terminal for a plain resume; resuming after an operator intervention is an open follow-up ([design](implementation-drive-design.md) §7).

- **Evidence.** `unattended_checks` adds four story criteria, read from the anchored story records of a single story feature and `blocked` in a planning run: `attempt-committed` (every terminal implementation attempt has a commit record, a sha or `empty`), `verify-observed` (the commit of every completed attempt has a verify record of its sha; a `needs-decision` attempt is committed, never verified), `status-synced` (the `done` status record's sha is on the branch) (a spec acceptance named by a `spec` status record whose commit is on the branch counts as current for `acceptance-current`, design §7 F10) and `deferred-recorded` (`trivial` without judgment-backed deferred items or accepted open highs, else the `done` status record carries one entry for each). `correction-observed` covers story corrections too: a verify correction must continue a red verify record of the attempt it corrects. Live (2026-10-11): `attempt-committed` and `verify-observed` passed on real records; the other two stayed `blocked` (no run reached `done`).

### Epic drive

One `epic start` drives every remaining story of an epic through the story drive above, in the epics file's order, on a branch the coordinator owns ([design](epic-drive-design.md), E1–E15; implemented 2026-10-18 with fake clients; live on the pilot project the same day, report: six epic runs, every stop passed through, one `--skip`, no story at `done`; design §6 and §7, F11–F15; the hook-18 findings F11–F15 landed 2026-10-19 with fake-client tests (designs D25, D26, E14, E15); live on a fixture with real Codex and Copilot workers the same day (live hook 19): two three-story epics to `epic-done`, every merge a fast-forward, the Copilot one with zero interventions, after F16 (the reviewer's attestation path, `bf55f91`); then on the pilot project the same day (live hook 20): Story 3.3 restarted with `epic resume --restart --roles` to `done`, the base sync merged the operator's commits twice, Story 3.4 to `done` after F18 (a spec author's `needs-decision` return may quote a question without its code marks, `339d9a2`), `epic-done` with Story 3.2 skipped; the client stop (D25) live on a fixture 2026-10-19 (live hook 21: nine stops continued inside an epic, `update-budget` and `epic resume --restart --roles` after them, the setup link through `{main_worktree}`, Codex judgments and corrections inside the epic)). The epic claims the repository once as `epic:<id>` with the token file and holds `drive.lock` for the whole run; per story it merges the base branch into the integration branch when that moved (only when `base` is a branch: a sha, a tag or a detached `HEAD` is not tracked), checks the story's `**Preconditions:**` bullets against `deferred-work.md` (met: `status: done` or a `decision:` line whose option label, less a leading date and leading punctuation or markup, does not start with `keep-open` or `keep open` in any case, with no keep-open line beside it), runs `story add` from the epic with the integration branch as base, fills the pipeline template, binds and leases it under the epic's session and runs the story driver; at `done` it merges `story/<key>` into the integration branch (`--ff-only`, else a `--no-ff` merge commit `epic(<N>): merge story/<key>` by `project.commit_identity`). The coordinator never pushes or merges the integration branch onward: at `epic-done` the operator opens the PR or merges where they point.

| Command | Mode |
| --- | --- |
| `epic start --token-file T --pipeline TEMPLATE [--max-turns N] [--deadline S] [--human-wait S] [--judgment-root P]` | stdin `{"epics_path", "epic": N, "branch"?, "base"?, "worktrees_dir", "story_defaults": {"writable_scopes", "project_clauses"?}, "stories"?: {"<key>": {"writable_scopes"?, "project_clauses"?, "roles"?: {"<role>": {"timeout"?, "max_turns"?}}}}}`. `TEMPLATE` is a story pipeline whose `feature_id` is `__FEATURE__` and whose step `story` blocks name `__KEY__` (`story_key`, and inside `spec_path`), with the spec chain. The branch (default `coordinator/epic-<N>`) is created at `base` (default `HEAD` of the `--repo` worktree) with the linked worktree `<worktrees_dir>/epic-<N>`; an existing branch or path is refused. `worktrees_dir` must lie outside the repository worktree. `--deadline` bounds the whole run (each story run gets the remainder), `--max-turns` each story run (the driver's turns, `RunBounds.max_turns`; a role's `max_turns` is the client's turn limit). A story's `roles` (design E14) is merged over the template's role for that story only (its sealed pipeline, and so its digest, differs from the other stories'), for roles the template names and within the pipeline's ranges; `epic start` checks every override against the bounds, `epic resume` only those of the stories still to run (not `done`, `skipped` or `already-done`, and not the story `--skip` or `--restart` names), every refusal naming the story; the deadline floor at a boundary uses the picked story's merged pipeline. |
| `epic resume --token-file T [--epic ID] [--skip KEY] [--restart KEY [--roles PATH]] [--max-turns N] [--deadline S] [--human-wait S] [--judgment-root P]` | continues the current story's run or the loop. `--skip KEY` leaves the story the last stop named to the operator: at once when it has no feature yet (`precondition-unmet`, `story-status`), else only after a run that ended `needs-human` or `failed` and while no attempt of it holds the fence. After a `release`, `--epic ID` with a token file that does not exist yet claims `epic:<ID>` anew and re-seals the current story's lease under the new generation. `--restart KEY` (design E15) applies to the story the last stop named under the conditions of `--skip`, and only to one with a feature (`restart-refused` otherwise): the epic records the restart (`restarts`: n, one above the feature's existing `epic-restart:<n>` decisions), revises the story's mandate (an operator-reported decision `epic-restart:<n>`, `constraints.restarts` and `constraints.restart_carry`: the blocking items of the review a `critical-finding` or `open-high-findings` stop names, or the failed command names of a `correction-budget` stop's red receipt, which every implement and spec author brief of the new revision renders JSON-quoted under `## Carried from the restart`), binds the template afresh at the new revision (the `--roles` JSON file `{<role>: {timeout?, max_turns?}}` becomes the story's override, else its recorded one stands; the story's box is checked against the bounds like a start's) under a new lease and runs the next attempt; corrections and updates start at zero, the spec chain stays satisfied by its status receipt (a restart before the spec carry writes the spec again), attempt commits and uncommitted files stay and are taken by the next attempt commit. A restart recorded but not yet run (for example after a kill before the story is leased again) is finished by the next `epic resume`; until then `--skip` and `--restart` of that story are refused ("… has a restart pending; epic resume runs it first"). `--restart` follows a terminal stop of the story's last run (`critical-finding`, `open-high-findings`, `correction-budget`, `update-budget`, `worker-blocked`, `attempt-resolved`); at any other stop it is refused naming the designed path (a decision or an accept), and the summary's `epic_action` offers it for those reasons only (ruling H10). `--skip` and `--restart` exclude each other, and `--roles` without `--restart` is refused (`INVALID_INPUT`); `counts.stories_restarted` counts this run's restarts and the story record carries `restarts`. |
| `epic status [--epic ID]` | read only, no token, no lock: every epic (newest first) with its state, `runs` (the number of its ended runs) and last summary; `--epic ID` lists that epic only and adds `drive status` of its current story's feature (an unknown ID is `NOT_FOUND`). |

The story drive's stops pass through unchanged (same `reason` and exit code, the story's `subjects` plus its `key`, `feature_id`, `lease_id` and `run_id`; the `operator_action` says `epic resume` where it said `drive resume`; the summary's `epic_action` names the skip, the restart (after a terminal stop, ruling H10) and the re-claim). The epic's own stops, all `needs-human`: `precondition-unmet` (record the decision on the base or the integration branch, then `epic resume`, or `--skip`), `story-status` (a story that is neither `backlog` nor `done`, or whose sprint key is missing or ambiguous), `integration-conflict` (a merge Git could not complete; the epic worktree is left clean; merge by hand in it, commit, `epic resume`), `worktree-drift` (the epic worktree off its branch or with uncommitted changes to tracked files). Below the deadline floor at a boundary the run ends `continue` (`deadline`) before any sync or `story add`. `epic-done` releases the session when nothing holds the fence. A `failed` story outcome ends the epic `failed` with the story's reason and writes nothing to Git; `story add` refusing a story (for example a `story/<key>` branch that already exists) ends it `failed` with `story-add`, the session kept.

Recovery: a story inside an epic is continued with `epic resume`; `drive resume` with the epic's token is refused (`epic-session`). A story that stopped terminally (`critical-finding` or `open-high-findings` with the corrections spent, `correction-budget`, `update-budget`, `worker-blocked`, `attempt-resolved` after an `attempt resolve`) is restarted with `epic resume --restart KEY` or left with `--skip`. A killed run resumes from the newest anchored state with `epic resume`, except a kill between the creation of the integration branch and the first anchored state: no record exists to resume from (`epic resume` refuses `run-unbound`), so release the session (`release --token-file T`), remove the epic worktree and the branch by hand (`git worktree remove <worktrees_dir>/epic-<N>`, `git branch -D <branch>`) and run `epic start` again with a new token file. After `failed` with `story-add`: remove `story/<key>` and its worktree (`git worktree remove <worktrees_dir>/story-<key>`, `git branch -D story/<key>`), then `epic resume --token-file T`; or `epic resume --skip <key>` to leave the story out. A kill inside `story add` (between its `worktree add` and the feature row) ends the next run the same way: the branch and the worktree are removed by hand. After the loop's own `stale-input` (a refused Git call, unreadable evidence, an unsafe path), `internal-error` or `corrupt-state`: repair, then `epic resume --token-file T`; or `release --token-file T`, then `epic resume --epic <id> --token-file <new file>`.

Evidence: `<common-dir>/coordinator/epics/<id>/template.json`, `state-<n>.json` (anchored `epic.started`/`epic.advanced`; the newest is the truth) and `summary-<n>.json` (anchored `epic.ended`); each story's lease carries `epic_id` and the session `epic:<id>`. The test criterion `integration-current` (`tests/drive_support.py`) scores whether the integration branch holds every done story's head and nothing but the coordinator's `epic(<N>):` commits above the newest one.
