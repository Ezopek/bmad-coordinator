## 1. Problem

The coordinator drives PRD and architecture work unattended (live runs 6–9, Copilot smoke 6), but has no story profile: a project at the implementation stage cannot be coordinated. The operator ran that stage with `bmad-loop` 0.13.1 on a pilot project (eight runs, 2026-10-02 to 04, 460 journal events). Of what stopped those runs, most was not about the product:

| What stopped a run | Count | About the product? |
| --- | --- | --- |
| CRITICAL escalation "no PostgreSQL available" (environment) | 1 | no |
| CRITICAL escalation from the orchestrator's own uncommitted ledger failing its clean-tree gate | 1 | no |
| "manual rollback required" because auto-rollback was off | 2 | no |
| three review sessions stalled on transport; the story was closed by hand and the findings were lost | 1 story | no |
| headless run crashed reading stdin for a decision (`EOFError`) | 1 | no |
| one-story cap reached, relaunch by hand | 4 | no |
| epic status never synced from story status | standing | no |
| intent gap against a binding contract | 1 | yes |
| sweep decisions pending | 5 | 4 yes, 1 process |

Plus ten token warnings that changed nothing and eight skipped reviews from a default policy. The orchestrator's facts came from markdown markers (`## Auto Run Result`, frontmatter status) and tmux silence; its interpretation came from scripts; its single deterministic strength was validating a result file field by field. The operator's three pains, in their words: workers do not commit, forget to write status, and stop on escalations that have nothing to do with the product.

The pilot's own build skill makes the same choices: `bmad-build-auto` requires subagents (else HALT `blocked`), commits by itself, writes `status: done` into the spec and HALTs `blocked` when the tree is dirty after finalization. Those are precisely the facts that must not be a worker's claim.

## 2. Goal and non-goals

**Goal.** One driver run takes one story whose spec is `ready-for-dev` to a reviewed, accepted, committed story branch and a synced status, with these properties: every fact (what changed, what passed, what is committed, what the status is) is taken from Git and from sealed receipts, never from a worker's text; every interpretation (what the worker meant, whether a question concerns the product, which recorded clause answers it) is a judgment with a receipt; the human is woken only by a closed catalogue of reasons, every one with an `operator_action`; nothing a worker or reviewer produced is lost.

**Non-goals (this slice).** Sequencing several stories of an epic in one run, parking between stories, parallel stories (the model allows them; the driver does not schedule them). Creating story specs (`create-story`, the attended planning route of `bmad-build`). Merging the story branch into the target branch, deleting worktrees or branches, squashing history. Installing the coordinator into a real project (the live proof uses a fixture; a pilot-project run is a separately authorized step). Running the project's commit hooks. Per-step judgment budgets (`max_judgments` keeps its whole-drive meaning). Changing any planning pipeline's validation, digest or behaviour: a sealed planning pipeline stays byte-identical and derives identically.

## 3. Decisions

### Story model and worktree

**D1. A story is a feature.** `story add` (new CLI command, token, stdin JSON `{spec_path, story_key, base_ref, worktree, writable_scopes, project_clauses?}`) reads the spec at the base commit and creates a feature through `create_feature`: `outcome` from the title and the Intent problem sentence; `constraints` from the "Always" list; `exclusions` from the "Never" list; `completion` from every Tasks & Acceptance item and every matrix row; `authority.delegated` from the numbered non-empty, non-heading lines of the frozen section (HTML comments, multi-line ones included, removed first; bullets stripped, table rows joined by ` | `, separator rows and each table's first row, its header, skipped by position; ids `S1…`), then `project_clauses` (ids `P1…`) (process rules such as "the coordinator commits; never ask whether to commit"); the spec's `context:` files are reading material for the worker and the reviewer, never clauses; `branch` = `story/<story_key>`; `base_ref` as given; `base_commit` resolved; `worktree` as given; the writable scopes as given (D3). The frozen section is the body between `<frozen-after-approval ...>` and its end tag, or between `<intent-contract>` and its end tag (both forms exist across BMAD versions); its text is stored content-verbatim (line endings normalized to LF, a BOM stripped; the binding's spec digest pins the file bytes) in the feature's `constraints_json` under `frozen_text` and rendered verbatim into every brief. Precondition: frontmatter `status` is exactly `ready-for-dev`; any other value is `INVALID_INPUT` naming the status found. A spec without a frozen section or without a Tasks & Acceptance section is refused the same way.

**D2. Linked worktree only.** `story add` always creates the worktree itself: `git worktree add -b story/<key> <worktree> <base commit>` (R12); an existing path and an existing `story/<key>` branch are refused, and a failed worktree add deletes the branch it created (nothing is left behind). A `worktree` argument naming the repository's main worktree is refused `INVALID_REPOSITORY`; the operator's own checkout is never a story worktree. The existing checks stay: HEAD of the worktree must be the story branch, `base_commit` must be an ancestor, `doctor` must find the installed package at the base. A launch checks the branch once; a worker's `git switch -c` or detached HEAD keeps the sha, so every coordinator write (attempt commit, verify, bundle, status) and the currency of an acceptance ask `symbolic-ref HEAD` again: another branch or a detached HEAD is `worktree-drift`. The store lives in the common dir and is shared by every story worktree; the one-lease-per-feature fence is unchanged.

**D3. The spec is read-only for workers.** The spec file, `sprint-status.yaml`, `deferred-work.md`, the coordinator package, `AGENTS.md`, `CLAUDE.md`, `_bmad/`, `.bmad-loop/` and the skill trees are protected paths of every story assignment (added to the generic protected set). As implemented: the spec, `AGENTS.md`, `CLAUDE.md`, `_bmad/`, `_bmad-output/` (the default home of the status files), `.bmad-loop/`, `.bmad-coordinator/`, `.agents/`, `.claude/`, a relocated `artifacts_dir` (D5, normalized before the comparison) and every `.gitignore` and `.gitattributes` at any depth (they change what Git stages, diffs and checks out; a worker return that adds or edits one the file inventory sees is refused `UNKNOWN_EVIDENCE`, §7); `story add` refuses a writable scope that covers the spec or one of the fixed paths, or lies inside one (`UNSAFE_PATH`), and prepare refuses a scope that covers `artifacts_dir` (`INVALID_INPUT`). A worker-created symlink or other non-regular file, or a mode-only change, inside the scopes is refused (`UNKNOWN_EVIDENCE`); deletions and renames inside the scopes are allowed and recorded (D8). Worker notes go into the return, never into the spec. The store is the truth about a story's state; the BMAD files mirror it (D18, D19).

### Pipeline and profile

**D4. New step kinds.** `KINDS` gains `setup`, `implement`, `commit`, `verify`, `status`. A story pipeline is: `compat` → `setup` → `status {phase: start}` → `implement` → `commit {of: implement}` → `verify {of: commit}` → `bundle {of: verify}` → `review {of: bundle}` → `accept {of: review}` → `status {phase: done, of: accept}` → optional `export`. Pipeline `format` stays 1; validation of a pipeline that uses none of the new kinds is unchanged, so every bound planning pipeline and its digest are unchanged. The `implement` step fields: `id, kind, author_id, story: {spec_path, story_key}`; it has no `skill`, `slug` or `inputs`. A pipeline mixes planning author steps and `implement` steps never (`INVALID_INPUT`): one story per pipeline.

**D5. Project profile.** The pipeline gains the required key `project` for story pipelines (absent and refused for planning pipelines): `{setup: [cmd...], verify: [cmd...], env: [NAME...], commit_identity: {name, email}, output_limit_bytes, rules?, artifacts_dir?}` where a `cmd` is `{name, argv: [...], timeout_seconds, cwd?}`. `argv` is executed without a shell; `cwd` is worktree-relative; `env` is an allowlist of variable names copied from the driver's environment, everything else dropped except `PATH`, `HOME`, `LANG`, `LC_ALL`. The placeholder `{changed_files}` in an `argv` element expands to the attempt commit's changed files that still exist (one argv element per file; a file name starting with `-` is passed as `./<name>`, so a worker cannot name a file into an option of the command; the element is dropped when the list is empty and the command is skipped with outcome `skipped`). `verify` needs at least one command (the gate is the point of a story pipeline); `setup` may be empty; command names are distinct; `commit_identity` needs a non-empty name and email; `rules` lists relative files the worker reads first; `artifacts_dir` (default `_bmad-output/implementation-artifacts`, where `sprint-status.yaml` and `deferred-work.md` live) must be a normalized relative POSIX directory without glob characters, and a writable scope covering it is refused at prepare. The whole `project` object is part of the sealed pipeline and therefore of its digest.

**D6. Return profile `bmad-implementation-v1`.** Registered in `profiles.MODULES` as module `bmad_implementation`. Extra required fields: `tasks` (array of `{task: str, done: bool}`), `verification` (array of `{command: str, exit_code: int, summary: str}`), `notes` (string). The brief labels `verification` and `tasks` as the worker's declarations. The generic rules on `changed_paths` are replaced for this profile only (D8).

**D7. The brief.** Rendered from stored rows by `bmad_implementation.prepare`, sections in order: *Read first* (spec path; the pipeline's project rule files; the spec's `context:` list), *Headless payload (verbatim)*, *Writable scopes* (the feature's writable scopes; protected paths named), *Story* (the frozen section verbatim; Tasks & Acceptance verbatim; the matrix verbatim), *Delegated authority clauses* (numbered, the only basis of a judgment's answer), *Recorded decisions* (the chain's resolving decisions, D21), *Verification* (the profile's commands with the sentence "run these before returning; the coordinator runs them again and only its result counts", and, F1: "if your tool policy denies a command, say so in `notes` and return `completed` anyway: a denied verification command is not a `BLOCKED:` condition"), a continuation section when the attempt continues an earlier one: *Correction after a recorded review* (correction round D4, unchanged) or *Correction after a failed verification* (the failing commands, their exit codes and their captured output, head and tail within `output_limit_bytes`, JSON-quoted so output cannot forge a heading) or *Continuation after a decision* (the recorded decision), and *Rules*: never run `git commit`, `checkout`, `switch`, `stash`, `reset`, `clean`, `rebase`, `merge`, `push` or `branch` or change the branch; never edit a protected path; one question per `needs-decision` and `options` naming the choices; a condition the worker cannot change is such a question whose text starts with `BLOCKED:` (a denied verification command is not one, F1), and `result: blocked` is only for a brief the worker cannot read (R4, D16); the standard return instructions otherwise. A continuation after an empty attempt (D11) is a fourth continuation section.

**D8. Git is the evidence of change.** For the implementation profile, `_return_evidence` does not compare `changed_paths` with the file inventory delta and does not refuse deletions or renames inside the scopes. It still refuses a change to a protected path or outside the writable scopes, a symlink or other non-regular file and a mode-only change (`UNKNOWN_EVIDENCE`), and still seals the `before`/`after` inventories as every profile does (R1). The observed delta is the cumulative Git delta of the working tree against the base commit (existing files in the writable scopes), computed when the return is observed and sealed as `git-delta.json` in the run directory; deleted and renamed-away paths are recorded in the profile payload, never in `changed_paths` (R2). The return's `changed_paths` is a declaration, stored as `claimed_paths`; the difference between the claim and the observed delta is recorded in the profile payload (`claim_delta: {unclaimed, unobserved}`) and rendered for the reviewer. The worker envelope's instruction text is profile-conditional: an implementation attempt is told this contract instead of the planning one. A worker's bookkeeping error is a fact, never the end of an attempt.

### Commit and verification

**D9. Attempt commit.** The `commit` step runs after every terminal attempt of its `implement` step (`completed-claim`, `needs-decision`, `blocked`), once per attempt. In the story worktree: check that HEAD is on the story branch (D2) and is the attempt's recorded parent (HEAD at prepare, stored in the binding as `parent_sha`), else stop `worktree-drift`; reset the index to HEAD (nothing staged by hand survives), then `git add -A -- <scopes>` for the writable scopes that exist or have tracked files; if nothing is staged and the attempt is `completed-claim` and HEAD is the `sha` of an anchored non-empty commit record of this feature at the current mandate revision, the attempt *stands on* that commit (F2, 2026-10-11): the record copies that record's `sha`, `parent`, delta, renames, `stat`, `message` and `diff_sha256`, carries `empty: false`, `stands_on: <that assignment id>` and this attempt's own number, and the patch `diff-<assignment>.patch` is written with the same bytes (a stood-on record is resolved to the record it stands on, so `stands_on` always names a real commit); if nothing is staged otherwise, record `empty: true` and no commit; else commit with `--no-verify` and the message `story(<key>): attempt <n> [<result>]` ending in the trailer line `Coordinator-Assignment: <assignment id>`. Every Git call of the receipts (the attempt and status commits and their reads) runs isolated: hooks disabled (`core.hooksPath=/dev/null`), `commit.gpgsign=false`, `core.fsmonitor=false`, an allowlisted environment (`PATH`, `HOME`, `LANG`, `LC_ALL=C`), a timeout, the project identity passed as `GIT_AUTHOR_*`/`GIT_COMMITTER_*`; the author, email and message are read back after the commit. Clean filters stay on (EOL and LFS fidelity). The record `commit-<assignment>-<digest16>.json` (sealed under `<common-dir>/coordinator/story/<feature>/`, anchored by `story.committed`, R8) holds `sha`, `parent`, the per-attempt `--name-status` delta and renames, `--stat`, the flags, the identity, the message, the attempt number and `diff_sha256`; the patch `diff-<assignment>.patch` beside it is `git diff --text --no-ext-diff --no-textconv --find-renames parent sha` (immune to `.gitattributes`). Attempt numbers are stable across resume. No schema change: `commit_sha` lives in the sealed record, not in the attempt row. Idempotence: before committing, the step looks for a commit above the base whose trailer names this assignment; it re-adopts that commit only when it reads back with the project identity and message (else `INVALID_REPOSITORY`), has a single parent, its parent is the attempt's parent and it touches in-scope paths only (else `BLOCKED_EVIDENCE`), and seals the record without committing again (a driver killed between `git commit` and the seal resumes correctly).

**D10. Setup and baseline.** The `setup` step runs once per worktree: each `project.setup` command in order, a setup record (per command: name, argv, cwd, exit code, duration, the output head and tail within `output_limit_bytes` with the digests of the whole output, outcome), then every `project.verify` command on the base commit in the same way, a baseline record. Before any command the step records `git --version` in the setup record; a Git older than 2.40 (the stat's `GIT_ATTR_SOURCE`, D9) seals a failed setup record with the reason "git >= 2.40 required" and runs nothing. A failing or timed-out setup or baseline command, or that preflight, stops the run `needs-human/verify-env` with `operator_action` "fix the environment so the setup and baseline commands pass (failed: …), then drive resume (setup and baseline are re-run); changing the commands needs a pipeline bound to a new mandate revision: release --token-file \<driver token\> first" (the `project` block is sealed with the pipeline). No client is launched before a green baseline. The records `setup-<digest16>.json` and `baseline-<digest16>.json` are sealed under `<common-dir>/coordinator/story/<feature>/` (anchored by `story.setup` and `story.baseline`); the step is satisfied when the newest setup and baseline records are green at the feature's base commit. A `verify-env` stop ends the run; `drive resume` derives `setup` ready again and re-runs it, and a second failure stops again (R11; no in-run retry). `story_facts` keeps the newest anchored record per kind and key; an unreadable newest record makes the fact absent, never a fallback to an older record.

**D11. Verification gate.** The `verify` step runs after every non-empty commit of a completed attempt whose HEAD equals the commit (a `needs-decision` or `blocked` attempt is committed, never verified): every `project.verify` command in order (none skipped on failure, each under its own timeout; a timeout is a failure with reason `timeout`), record `verify-<assignment>-<digest16>.json` (anchored by `story.verified`; `commit_sha`, per command `{name, argv, cwd, exit_code, duration_seconds, stdout, stderr, stdout_sha256, stderr_sha256, truncated, outcome}`; outcome `pass`, `fail`, `timeout`, `skipped`), the captured outputs inline as head and tail within `output_limit_bytes`. A green receipt is the precondition of the bundle step. A red receipt triggers a correction while `max_corrections` lasts (D12; no default: set it explicitly, the example uses 3). An empty attempt (D9) skips `verify`; a `completed` attempt that stands on an earlier attempt commit (D9, F2) is not empty: it is verified, bundled and reviewed on that commit under its own assignment id (a verify receipt, a bundle and a review of its own), so a worker that writes first and asks second, or a correction whose answer the code already satisfies, reaches the gate; a correction that changes nothing spends its correction and, after a red verify, ends in `correction-budget` naming the failing commands rather than in `worker-blocked` "no change produced" (the red receipt on the branch is the better fact). An empty attempt that returned `completed` (nothing to stand on: HEAD is the base or a status commit) gets one continuation prepared without a judgment ("Your return said completed but the working tree is unchanged. Implement the story, or return `needs-decision` with one question starting with `BLOCKED:` naming the condition."), counted in `max_updates`; a second empty `completed` stops `needs-human/worker-blocked` with the condition "no change produced" (D17).

**D12. Correction after verification.** `PlanningPrepare`'s correction fields get a sibling in `ImplementationPrepare`: `corrects_verify: str | None` (the verify receipt ref), exclusive with `corrects_review`, `continues_request` and `empty_attempt` (D11). The trigger lives in the `implement` step's head derivation, as the review correction does: head observed, commit non-empty, verify receipt red, corrections used below `max_corrections` → prepare the correction with the D7 section. Verification corrections and review corrections share `max_corrections`. `max_corrections` has no story default: the key stays optional and absent means `0`, as for planning pipelines, so a story pipeline sets it explicitly (the usage example and the tests use `3`); the cap is `MAX_CORRECTIONS = 6` for story pipelines only, while a planning pipeline keeps the cap `4`. A red verify with the budget spent stops `needs-human/correction-budget` with subjects `{corrections: {used, max}, verify_ref, failed}`; the red receipt is final, so the stop is terminal for a plain resume (D17).

### Bundle, review, acceptance

**D13. Code bundle.** `bundle_for_workspace` gains a sibling `bundle_for_commit`: the core bundle manifest (the artifacts are the head attempt's observed cumulative change, plus contributors and contract files) with `commit: {sha, parent, assignment_id, diff_sha256}`, sealed with copies of the changed files; the diff lives in the attempt's commit receipt (`diff-<assignment>.patch` beside the commit record, D9) and inline in the review brief within `output_limit_bytes` (R3). `bundle_for_commit` needs HEAD on the story branch at the commit and the writable scopes clean (`git status --porcelain -- <scopes>` empty), so the sealed copies are the commit's bytes; else `worktree-drift`. An implementation bundle must be commit-bound: the profile gate validates the manifest `commit` (its keys, a hex object id, a contributor's assignment, equality with that attempt's anchored commit record) at bundle, accept and verify, and at bundle also that the artifacts equal the attempt's observed change. Currency for this bundle kind: the newest verify record of the commit's attempt passed on that commit (D15); HEAD is on the story branch (D2) and equals the commit, or descends from it (`merge-base --is-ancestor`, so a reset below the bundle is drift) with every commit above it the commit of an anchored `story.status` record of this feature (a trailer in a message is no evidence), and the writable scopes are clean. The reasons make an acceptance `unknown` through the core `verify`; the file-level `source_state` is unchanged.

**D14. Code review.** `review_prepare` with a code bundle renders the review brief from: the frozen section, the clauses, the decisions (the bundle manifest's: the head's resolving decisions and the chain's resolving decisions sealed in the head's binding, D21, so a decision that resolved an earlier attempt's question reaches the reviewer, F3), the verify receipt summary (command, outcome, exit code), the diff inline (head and tail within `output_limit_bytes`; a missing or digest-mismatching patch refuses the review prepare `BLOCKED_EVIDENCE`), the changed file list, the worker's `tasks`, `notes`, `verification` and the `claim_delta` labelled as declarations, and the carried items of earlier reviews of this feature (as implemented, only planning contributors' carried items; the open findings of an earlier code review are not rendered yet, §7). Fixed review focus, in the brief, as the pinned lens set `acceptance`, `matrix`, `scope`, `security`, `regression` (R9; review prepare refuses another set for a commit-bound bundle): every acceptance criterion separately (an unmet criterion is `critical`); every matrix row's coverage by a test that ran in the verify receipt; scope (a change outside the Intent is `high`); protected paths; security; regressions in the code the diff touches. The finding schema is unchanged; `location` is `path:line` at `commit_sha`. The reviewer client runs read-only in the story worktree (the existing read-only modes; Git reads allowed by them, no process execution required).

**D15. Acceptance.** `blocking_findings` and `accept_on_high` are unchanged. `accept` requires the bundle current (D13) and a passing verify record of the same `commit_sha`: the newest `story.verified` record of the commit's attempt names that sha with outcome `pass`. The derivation reaches `accept` only after a green verify, and the profile gate enforces it at accept and verify too, so an attended `bmad accept` of an unverified or red commit is refused and a later red re-verify makes the acceptance `unknown`. A review correction (`corrects_review`) runs as in the correction round and then passes through `commit` → `verify` → `bundle` → `review` again; the correction budget is shared (D12). After acceptance, an unrecorded commit above the bundle commit while the `done` status is unsealed is left to the `status done` step instead of an `acceptance-stale` stop: the step re-adopts its own trailer commit on the accepted commit (a driver killed before the seal) and refuses anything else (`worktree-drift` or `BLOCKED_EVIDENCE`); then currency applies again.

### Judgment and stops

**D16. Reversibility.** Judgment schema v3 (`coordinator-judgment-v3`) adds the top-level verdict `defer` and the `deferred` list (`answer` when every answer cites a clause, `defer` when at least one is deferred); `refuse` keeps its meaning and refusal is whole-request, so a `defer` that carries refusal text is a defect (`refusal-on-defer`). Planning requests keep v2 (R10). A worker never routes a condition through `result: blocked`: the brief says a condition it cannot change is returned as `needs-decision` whose one question starts with `BLOCKED:`; a `blocked` return stops `needs-human/worker-blocked` as today (R4). For a question with no authorizing clause the brief instructs: classify it against the closed **binding** list (persisted data shape: schemas, migrations, stored formats; external contracts: API routes and payloads, CLI flags, file formats read by others; security, permissions, authentication; user-visible behaviour contradicting or beyond the Intent; deleting or renaming public things; new dependencies); a choice that a later code change cannot undo is binding too, so reversibility is a gate. Binding, or uncertain → `refuse` the whole request with `refusal` naming the category. Otherwise → `defer`: choose the minimal, conservative choice closest to the frozen story (the judgment reads it from `mandate.json` `fields.constraints.frozen_text`), state it as the answer text with an empty clause, and add one `deferred` entry `{index, title, context, choice, revisit_when}`. A `defer` is recorded as a `coordinator` decision whose `source_ref` is `mandate:r<rev>:deferred+<cited ids>:authority;receipt=<ref>#<sha256>` (`mandate:r<rev>:deferred:authority;…` when every answer is deferred and nothing is cited) and whose `choice.deferred` carries the entries; the derivation continues the attempt with it exactly as with an answer. A `refuse` on a product question stops `needs-human/product-decision` (a new reason in `REQUEST_REASONS`, with the question, the worker's options and the refusal text in the subjects; the options are not sealed for the judgment itself, §7); so does any other observed judgment of a story request that is not a valid `answer` or `defer` (a defect such as `refusal-on-defer`; the subjects then carry the defects). A request with more than one open question is resolved by a driver-recorded `coordinator` decision (`source_ref` `driver:form`, `choice.form_refusal: true`) and continued as an ordinary request continuation whose brief says to ask one question per return, counted in `max_updates`; no judgment is launched (R6).

**D17. Stop catalogue.** Reasons a story drive may stop with `needs-human`, each with `operator_action` and a resume path:

| Reason | When | Resume |
| --- | --- | --- |
| `product-decision` | a binding question outside every clause (D16) | `inbox add decision`, `drive resume` |
| `worker-blocked` | a `blocked` return (R4: conditions travel as `BLOCKED:` questions), or a second empty `completed` attempt ("no change produced", D11) | terminal for a plain resume: with the driver's token while no driver runs, revise the mandate and record its compat decision, `release`, then `drive start` a pipeline bound to the new revision; or release and finish attended |
| `question-conflict` | the worker contradicts a recorded decision or the frozen section (existing) | a narrowed decision, resume |
| `verify-env` | red setup or baseline, or Git older than 2.40 (D10); the run ends | fix the environment so the commands pass, resume (setup and baseline are re-run, R11); changing the commands needs a pipeline bound to a new mandate revision (release first) |
| `correction-budget` | a red verify with `max_corrections` spent (D12) | terminal for a plain resume: fix the failure by hand in the story worktree without committing, then as for `worker-blocked` (the next attempt's commit takes the fix); or release and finish attended |
| `judgment-budget`, `update-budget` | judgments (whole drive) or updates spent | `judgment-budget`: `inbox add decision`, resume; `update-budget`: release, attended repair, `drive start` |
| `critical-finding`, `open-high-findings` | a blocking review with the correction budget spent (existing) | as today |
| `client-failure` | **Follow-up, not in the first slice:** `client_failures` consecutive attempts of one step ended without a return (unknown, 429, crash, timeout) | resume retries; `attempt resolve` as today when needed |
| `worktree-drift` | HEAD is not on the story branch or not the expected commit at `commit`, `verify`, `bundle` or `status`, or the writable scopes changed after the attempt commit (`bundle`) (D2, D9, D13, D18) | switch back to the story branch, `git reset --mixed` to the recorded commit if HEAD moved (a hard reset destroys the worker's uncommitted attempt), remove stray changes in the scopes, resume; or release and finish attended |
| `status-shape` | a project status file the coordinator cannot edit safely (D18); the detail names the line and every file is left unchanged | fix the file in the story worktree without committing it (the status step needs HEAD at the base or the accepted commit and commits the file itself), resume; or release and finish attended (an unreadable `deferred-work.md` at HEAD cannot be fixed in the working tree) |

The driver's integrity stops (`ownership-lost`, `mandate-revised`, `stale-input`, `attempt-resolved`, `judgment-preflight`, `signal-stop`, `operator-stop`) keep their names and meaning; each is raised only by an operator's act or a configuration fault, never by a worker's output. `client_failures` is deferred: an attempt without a return still needs the operator's `attempt resolve`, because the fence is released on operator evidence by design (unattended-driver design §3). The `operator_action` texts are the driver's (`drive.py` `_operator_action`); "resume after an operator intervention" on a terminal story stop is an open follow-up (§7). Nothing else stops a story drive: a stall is a client timeout, which ends the attempt without a return (`attempt-unknown`, as above); a dirty tree is committed (D9); status is a coordinator step (D18); a mismatched claim is a fact (D8); a process question is answered from a project clause.

### Status and deferred work

**D18. Status step.** The `status` step is a coordinator step with no model, run twice: `phase: start` before the first attempt and `phase: done` after acceptance. Each run edits files in the story worktree and commits them with the trailer `Coordinator-Status: <feature id> <phase>` (message `story(<key>): status <in-progress|done>`, `--no-verify`, `--allow-empty` so the trailer commit always exists, isolated as D9). The status files are `<artifacts_dir>/sprint-status.yaml`, the spec and, at `done`, `<artifacts_dir>/deferred-work.md` (D5); a status commit may touch only them. The start commit sits on the base commit, the done commit on the accepted commit; HEAD elsewhere is `worktree-drift`. Start: `development_status.<story_key>: in-progress` in `sprint-status.yaml`; the story's epic (`epic-<n>` for a key `<n>-…`) `backlog` → `in-progress`; spec frontmatter `status: in-progress`. Done: `development_status.<story_key>: done`; the epic `done` when every key of that epic in the file is `done` (a quoted `'done'` counts; the epic rule reads values unquoted); spec frontmatter `status: done` and an appended section `## Coordinator Result` (acceptance id, accepted commit, review id, verify summary, judgment decisions with their ids). The files are edited textually, line by line, preserving comments, order, CRLF line endings and a BOM; an unknown key or file shape stops `needs-human/status-shape` with the line reported (D17), and every edit is computed before any write, so a shape stop leaves every file unchanged. The status files are staged as literal paths (`GIT_LITERAL_PATHSPECS=1`), so a `[` or `*` in the spec name stages that file only. HEAD must be on the story branch (D2). Idempotence as D9: a `Coordinator-Status` commit for this feature and phase above the base is re-adopted only when it reads back with the project identity and message (else `INVALID_REPOSITORY`), has a single parent, the expected parent and touches the status files only (else `BLOCKED_EVIDENCE`); the driver reports either refusal as `needs-human/stale-input` with the detail, never as a stale acceptance.

**D19. Deferred work.** In the `done` phase the coordinator appends to `deferred-work.md` one canonical entry per deferred item of a judgment-backed decision (D16) and one per open `high` finding of the accepted review, in the project's entry format: `### DW-<n>: <title>` with `n` = the greatest existing number plus one, then `origin: coordinator <decision id | review id>`, `location:` (the finding's location or the spec path), `source_spec:` (the spec file name), `severity:` (`medium` for a deferred item, `high` for a finding), `reason:` (a deferred item's context and `Revisit when: …`; for a finding "accepted under accept_on_high: …" when the pipeline sets it, otherwise "accepted attended after an open-high-findings stop: …", then its consequence), `status: open`, and `decision: <date> <choice>` for deferred items, the date taken from the judgment's sealed `classified_at`. Every field is written on one line, so recorded text cannot forge a heading or a `status:` line. The file is append-only; a missing file is created with its first entry. No finding of a recorded review and no deferred decision is left only in the store.

**D20. What remains.** After `done`: the branch `story/<key>` with the chain status(start) → attempt 1..n → status(done); the worktree in place; the lease released; the sealed receipts in the common dir; the export as today. The operator's checkout and the target branch are untouched; merging is a human act outside the driver (D-009 in the handoff: a reviewed, committed local branch is the result).

**D21. Chain decisions and Claude worker commands (2026-10-11, F1 and F3).** The driver passes every story prepare the chain's resolving decisions: `decisions` = `[{id}]` of every decision that resolved a request of a bound, non-cancelled implementation assignment of this feature at the current mandate revision (`service.resolving_decisions` over those assignments), sorted by id; prepare validates them as today (a current decision of this feature, else `INVALID_INPUT`), the binding seals `{id, digest}` and the brief lists them under *Recorded decisions* (a `continues_request` update also repeats the resolving decision in its continuation section). The bundle manifest therefore carries them (`bundle_decisions` reads a contributor's sealed `decisions`), the code review brief renders them (D14) and the acceptance's decision check covers them. When the worker client is `claude-code`, the story binding seals `commands`: the sorted distinct `argv[0]` of `project.setup` and `project.verify` (an `argv[0]` that is not pattern-safe, `clients.pattern_safe`, or more than `MAX_COMMANDS` distinct values refuse the prepare `INVALID_INPUT`), so the launch renders `Bash(<argv[0]> *)` rules and the worker can run the project's commands. Operator decision 2026-10-11: every test runner executes code the worker wrote, and `Bash(python3 *)` allows `python3 -c …`, so a Claude story worker then runs arbitrary code as the operator: it can write anywhere, inside and outside the worktree (the Edit/Write deny rules stop guarding the protected paths), reach the network and read the inherited, unscrubbed environment (`ANTHROPIC*` and other unprefixed operator variables); the return-time inventory, the scope checks and the contract digests remain the audit, and they cover the worktree only (the exfiltration surface F4 names is therefore open for a Claude story worker today); a project command whose `argv[0]` is `git`, a shell or an interpreter widens the rule to that whole program (the brief's Git rules then hold only at the audit), so the operator chooses the project commands with that in mind. Other worker clients get no `commands` from the project block (Codex runs commands in its sandbox; Copilot's `commands` are `uv run` launcher forms).

**D22. A story drive stands without the planning contract (2026-10-13, F5).** A story worker invokes no BMAD skill, the code review brief defines its five lenses itself (R9) and names only the story spec as reading, so nothing a story reads lives in the installed BMAD contract. The only ties were the `compat` step (`bmad discover` supported, a compatibility decision, no drift), the briefs directory resolved by executing the project's `_bmad/scripts/resolve_config.py` (`central_path(core.output_folder)`) and the contract files sealed in every story binding and bundle manifest, which no gate of the story path reads. The pilot (§7 F5) showed the cost: a project that git-ignores its BMAD trees has none of them in the linked story worktree, so the drive stopped `compat-review` until the operator copied the ignored trees by hand. The story drive drops all three ties; planning keeps every one of them.

- *Pipeline.* A story pipeline (one with an `implement` step) has no `compat` step: one present is `INVALID_INPUT` ("A story pipeline takes no compat step"), so the chain starts with `setup`. A planning pipeline keeps its first `compat` step and every rule of the unattended driver design. For a story pipeline the driver gathers no contract facts (`facts["contract"]` is `None`: no `bmad discover`, no `central_path`, no resolver process per turn) and derives the story prepare and the code review prepare without a `compat_decision_id`.
- *Story prepare.* `ImplementationPrepare` loses `compat_decision_id`. Prepare runs no discover and judges no decision, so `UNSUPPORTED_CONTRACT` and the compatibility `BLOCKED_EVIDENCE` leave the story path; the binding seals no `fingerprint_sha256`, `contract` or `compat_decision_id`, and the assignment seals no contract files (`contract_files` `[]`, `contract_digest` of the empty canonical list), so the attempt's bundle manifest carries no `contract` entries and `_artifact_contributors` matches the story's attempts on that empty record. The core therefore accepts an empty contract list for an assignment and for a bundle: the contract-list file checks of `create_assignment`, of the launch reservation and of `bundles.capture` run only over the entries given (an empty list passes; the source digests still need the brief), and the manifest, `verify`'s record comparison and the contributor grouping work on the empty list unchanged. A story's reading material beyond the spec (`project.rules`) stays unsealed as before (§7). The brief and the spec stay the sealed sources, and the scope check keeps the brief: a writable scope covering the briefs directory is `UNSAFE_PATH`.
- *Briefs directory.* The `project` block gains the optional `briefs_dir` (default `_bmad-output/coordinator/briefs`, the location the central config resolved so far, so an existing story layout does not move): the `artifacts_dir` grammar (a normalized relative POSIX directory without glob characters, not `.`), with the first segment neither `.git` nor `.bmad-coordinator`; it is sealed with the pipeline and part of its digest. The story brief is `<briefs_dir>/<key>.md`; `protected` (D3) covers the directory as it covers `artifacts_dir`, so a worker write there is refused at return whatever the directory's name. The code review brief of a commit-bound bundle goes to the same directory, read from the sealed `project` of the bundle's implementation contributor (one pipeline seals one project block, and every contributor of a story bundle is an attempt of that pipeline), so `review_prepare` never calls `central_path` for a code bundle.
- *Code review.* `ReviewPrepare.compat_decision_id` becomes optional. For a commit-bound bundle it must be absent (`INVALID_INPUT`, "A code review takes no compatibility decision"); `review_prepare` then runs no discover, checks no contributor fingerprint, seals no contract files and no `fingerprint_sha256`, `contract` or `compat_decision_id`. For a planning bundle it stays required and the prepare is unchanged. The review gate skips `check_binding` for a binding without `fingerprint_sha256` (a code review binding) and keeps the rest: live bundle bytes at reserve, the whole proof at accept and verify.
- *Unchanged.* Planning prepare and the planning review (`check_binding`, drift `STALE_INPUT`), `bmad discover` and `decision add` for a fingerprint, D21's `commands`, `story add` and its protected set (`_bmad/`, `.agents/`, `_bmad-output/` … stay protected whether or not they exist in the worktree), the isolated receipts (D9). A project that git-ignores its BMAD trees, carries another BMAD version or has no BMAD installation at all runs a story the same way; F5's copy step leaves the usage doc. The story drive no longer executes the project's resolver scripts on the coordinator's behalf: beyond Git's own hooks (§7: `story add`'s `git worktree add` runs the repository's `post-checkout` hook), the project's own `setup` and `verify` commands are the code-execution surface of a story, which narrows the installation note of the pilot report. *Legacy pipelines (ruling P5 during the implementation, 2026-10-13).* A story pipeline sealed before D22 carries a `compat` step and no longer loads: `drive resume` refuses it (`INVALID_INPUT`; a new mandate revision binds a new pipeline) and `drive status` lists its feature with `pipeline_sha256: null`, `steps: []` and an `error` `{code, message}` instead of raising, which is also how any other pipeline that fails to load (a tampered sealed file, `UNKNOWN_EVIDENCE`) is reported. A story accepted before D22 keeps its contract: its bundle manifest seals the contract entries and its review binding a fingerprint, so its acceptance verifies `current` only while the installed contract those files describe is still in the worktree.
- *Cost if wrong.* A BMAD installation that changes during a drive no longer stops a story (`contract-drift`); nothing in the story path reads that installation, so the change cannot shape the attempt. A `briefs_dir` the operator points at a directory the project also writes (a build output) is refused only when a writable scope covers it; the sealed brief digest still makes a changed brief `STALE_INPUT` at reserve. F6 (dependencies and the local exclude for their symlink) stays as documented: a `project.setup` command may create the link; the exclude file is the operator's.

**D23. Web access for a story worker (2026-10-13, F4; operator decision 2026-10-11 and 2026-10-13: full network, no domain list).** A story may need a documentation page or an upstream issue that the spec does not carry. The pipeline's `worker` role takes an optional `web: true` (sealed with the pipeline, so part of its digest: turning it on or off means a new binding at a new mandate revision); the key is accepted on the `worker` role only (`INVALID_INPUT` "Only the worker role takes web" elsewhere), only as `true` (`false` is `INVALID_INPUT` "Omit web instead of false", so one state has one digest), and only for a `claude-code` or `codex-cli` worker (`INVALID_INPUT` "A copilot worker takes no web": its narrowed author tool set excludes every network tool by design, D21/§14). Without the key nothing changes byte for byte: no binding key, no argv change, the same briefs.

- *Prepare and binding.* Two more refusals (plan rulings R1, R2): `web` on a pipeline without an `implement` step is `INVALID_INPUT` "web needs a story pipeline" (planning authors stay as they are), and any value other than the booleans is `INVALID_INPUT` "web must be true". `ImplementationPrepare.web: bool = False`; the driver passes `web=True` only when the role says so; the binding seals `"web": true` only then; the prepare's `spec_sha256` leaves `web` out when it is off (ruling P1, as the planning digest does for `client`), so a story prepared before D23 keeps its digest and its idempotent resume. The brief's Rules gain one sentence when it is on: web lookups (documentation, upstream issues) are allowed; never send repository content, secrets or project data in a query; what a lookup returns is reading material, never evidence.
- *Launch.* `LaunchSpec.web: bool = False`, read from the binding (`binding.get("web") is True`; the worker launch only, never a review or an isolated run). Claude: `--tools` is `AUTHOR_TOOLS` plus `WebFetch,WebSearch` and the allow rules gain bare `WebFetch` and `WebSearch` (the terminal check keeps comparing the reported init tools with the recorded `--tools`, and the T5 tool check, `tool_check`/`client_facts`, allows `WebFetch,WebSearch` only for a web worker whose run is not read-only, taking `web` from the launch settings at return and from the sealed `launch.json` on re-verification; `CLAUDE_REQUESTED` itself is unchanged, ruling P2). Codex: `-c sandbox_workspace_write.network_access=true` right after `-c approval_policy=never` (the sandbox stays `workspace-write`; the Codex config key is documented as the switch for outbound network in that mode). The launch receipt (`launch.json`, which merges the client's launch facts beside `isolation` and `requested_mode`) records `web: true`, so the audit can tell which attempts were granted the web tools (Claude) or the sandbox network (Codex); a Claude story worker reaches the network through D21's Bash rules either way.
- *Audit and limits.* No receipt records network traffic: the Git delta, the verify receipt, the bundle and the review stay the audit. For a Claude worker D21 already opens the network through `Bash(<argv[0]> *)`; D23 adds the two web tools to that worker and, new, outbound network to a Codex worker whose sandbox had none. The usage doc states this surface once beside D21's.
- *Unchanged.* Reviewer and judgment launches (read-only, no network), planning authors, the `project` block, every client's environment scrub.
- *Cost if wrong.* A worker with `web: true` can send what it reads to any host; the operator turns the key on per pipeline, with that sentence in front of them, for a story that needs it.

**D24. The story drive writes its own spec (2026-10-15; operator decision 2026-10-14: the coordinator's own brief, not a BMAD skill; the human answers decisions, not specs).** Today a story needs a `ready-for-dev` spec written by hand before `story add`. D24 moves spec authoring into the story pipeline as its first step, keeps the human at the decisions a spec cannot settle, and leaves the chain from `setup` down unchanged except its start commit (ruling P7 of the plan: after the spec chain the setup baseline and the start status commit sit on the `spec` status commit, not the base commit).

- *Story from the epic.* `story add` takes `spec_path` or, new, `epic_story: {epics_path, story_key}` (one of the two): the story key must exist in `sprint-status.yaml`'s `development_status` at `backlog` or `ready-for-dev`, and `epics_path` must hold the heading `### Story <N>.<M>: <title>` whose number is the key's `<N>-<M>` prefix. The feature's mandate is then provisional: `outcome` from the story title and its "As a / I want / So that" lines, `completion` from the story's `**Given**/**When**/**Then**/**And**` acceptance lines, `constraints`/`exclusions` empty, `authority.delegated` the `project_clauses` only (ids `P1…`); `constraints_json` records `epic_story` and `spec_path` = `_bmad-output/implementation-artifacts/spec-<key>.md` (which must not exist at `base_ref`; a pipeline with a `spec` step therefore keeps the default `artifacts_dir`, refused at bind otherwise), and the spec path joins the feature's writable scopes for the spec author while implement attempts never get it (ruling P3). The worktree, branch and base are as in D1. A `Preconditions:` block under the story heading is read into `constraints_json["preconditions"]` (one line each) for the brief; the coordinator does not evaluate them.
- *The `spec` step.* A new kind in a story pipeline, allowed only first (before `setup`), `author_id` as for `implement`, and only when the feature was added with `epic_story` (a feature with a hand-written spec takes no `spec` step: `STALE_INPUT` at bind, and a feature added from an epic needs one). Its chain is `spec` → `bundle` (`of` the spec step) → `review` (`of` that bundle, `reviewer_id` distinct from the author) → `accept` (`of` that review) → the existing `setup`. The attempt runs in the story worktree with the writable scope `[<spec_path>]` only (the file itself, D3's protected set unchanged: `artifacts_dir` stays protected for everything but that file), on the `worker` role's client with `web` if set, commands `[]` (no project command runs during authoring; a Claude author therefore gets no Bash rule). Prepare, binding, brief, return receipt and commit follow the implementation profile's machinery (D6–D9) under the profile name `bmad-spec-author-v1`: the return adds `open_questions: [{id, question, options: [{label, consequence}], recommendation}]` (ids `Q1…`, the same entries the spec's `## Open Questions` section holds, so the return and the file are checked against each other at return: a mismatch is `UNKNOWN_EVIDENCE`) and `assumptions: [text…]`; `tasks` and `verification` are absent. The commit (D9's `story(<key>): attempt <n> [<result>]`, by the coordinator; the attempt numbers run over both kinds) holds the spec file only; an empty attempt is `worker-blocked` as today.
- *The brief.* The coordinator's own text (no skill): the story entry from `epics.md` verbatim (title, user story, acceptance lines, preconditions), the compiled epic context the operator may name in the pipeline's new `project.context` list (relative files, read first; for example a PRD, an architecture document, `epic-<N>-context.md`), the `done` specs of the same epic found in `artifacts_dir` (paths only, read if useful), `project.rules`, the story's code scopes (a change the story needs outside them is an Open Question, never a task; F9), the spec template (the `<frozen-after-approval>`/`intent-contract` body: Intent, Boundaries, matrix; then Open Questions, Code Map, Tasks & Acceptance, Verification) with the pipeline's own `verify` commands as the Verification section, and the rules of the "plan" step of the BMAD build skill restated: investigate the repository first and ask nothing; one story, one user-facing goal, 900–1600 tokens; an **Open Questions** entry only for an intent gap (what the request does not say, the code cannot settle, and the user would notice in the result), each with options and consequences and a recommendation; every other choice is the author's, recorded in the spec; an unmet precondition is a `BLOCKED:` question naming the ledger entry; frontmatter `status: 'draft'` while any entry remains, else `ready-for-dev`; write only the spec file.
- *Spec review.* The code review lens set does not fit a spec; a spec bundle is reviewed with the fixed set `SPEC_LENSES` = `readiness` (the READY FOR DEVELOPMENT standard: every task names a file and an action, ACs Given/When/Then, no placeholder, no contradiction), `scope` (one user-facing goal, one story, no second deliverable; a task outside the story's code scopes is `high`, F9), `verification` (the Verification commands are the pipeline's and would exercise the matrix), `edges` (the matrix covers the inputs a reasonable person would try; an unanswered intent gap hidden in the prose instead of Open Questions is `critical`), `fidelity` (nothing in the spec contradicts the epic entry, the context files or a recorded decision). The spec review brief also lists the delegated clauses (at r1 the `P` clauses) and `project.rules`, and `fidelity` covers the project clauses. Severity, corrections and `accept_on_high` work as for a code bundle, with `max_corrections` counted per kind (ruling P5: spec corrections and code corrections are separate loops); `critical_open` blocks as today.
- *Decisions.* Questions arrive through the existing request flow (ruling R1): the spec author returns `needs-decision` with all its Open Questions at once (the one-question rule is for implement attempts), and the judgment (v3) runs per request with the spec's own options and the author's recommendation in its brief: `defer` or `answer` under a delegated clause resolves a reversible question (recorded, the deferred ones as `deferred-work.md` entries at `done`, D16) and the author's continuation (intent `update`, `continues_request`, the decisions as D21 renders them) writes the answers into the frozen section, removes the answered entries and sets `ready-for-dev`. A refused (binding or uncertain) question stops the run `needs-human/spec-decisions` with `subjects: {step_id, assignment_id, request_id, spec_path, questions: [{id, question, options, recommendation}], digest}` and the `operator_action` "inbox add decision for request <id> (choice {\"answer\": <text>} answering every question, or {\"recommendations\": true}), then drive resume": one decision answers the whole request, since a request has one resolution. The `digest` renders the spec's frozen section as the author wrote it: the Intent problem and approach sentences, each matrix row as "when <input>, then <expected>", the Always list (ruling P8) and the Never list. The review runs once on the completed spec, with the same brief on every round. **Accept.** `spec_auto_accept: true` lets the driver accept the reviewed spec; without it the accept is the human's (ruling P6), also after answered questions, because the continuation rewrote the frozen section the human saw and that section becomes the story's delegated authority: the reviewed spec stops `spec-decisions` with `questions: []`, the digest, `clauses` (every `S<n>` line the carry will delegate), the bundle and the review. The operator either accepts it (`bmad accept review` with the driver's token while no driver runs, then `drive resume`) or sends it back (ruling P13): `decision add` with the driver's token, `source_kind` `operator-reported`, `source_ref` `spec-revise:<bundle_id>` and `choice: {"revise": <text>}` at the feature's revision, after which the spec step prepares an author `update` carrying that decision (counted in `max_updates`), and the revised spec is committed, bundled, reviewed and stops for the accept again. **Carry.** The accepted spec is the mandate: `sync_status` phase `spec` commits `story(<key>): spec ready-for-dev` and seals the `story.status` record with `source_id` `spec` (the receipt); on the next turn the driver's `carry` action records a `coordinator` decision `spec-ready:<status sha>`, revises the feature (mandate revision +1: `constraints`, `exclusions`, `completion`, `authority.delegated` from the frozen section as D1 reads them, the `S` clauses then the `P` clauses; `provisional` dropped), binds the pipeline value equal to the bound one except `mandate_revision` and re-seals the lease (a second `drive.leased` record of the lease id, `carried_from` the old digest; the summary counts `carries`), so the run continues without the `mandate-revised` stop and every later brief, binding and judgment sees the spec's clauses exactly as for a hand-written spec. The carry refuses a status commit whose frozen section differs from the accepted spec's, and finishes a carry interrupted by a kill only while the feature's revised mandate is the one the spec yields (else the run stops `stale-input`: the mandate moved other than by this pipeline's carry). At the new revision the `spec` step and its wrappers are satisfied by that receipt while its commit is on the branch, never by the r1 acceptance, which the core marks stale on revision; a receipt whose commit left the branch stops the spec step `worktree-drift` instead of deriving the chain again; later step keys use the carried digest's prefix.
- *Status.* `sync_status` moves the sprint-status key to `ready-for-dev` in the spec's accept commit (`story(<key>): spec ready-for-dev`, trailer `Coordinator-Status`, the spec frontmatter flipped by the coordinator, never by the author) and the existing `status start` step moves it to `in-progress` as today. The `spec` status step refuses a worktree spec whose bytes differ from the accepted commit other than by its own status flip (`worktree-drift`, rulings P8 and P11), so no unreviewed text reaches the carried authority.
- *Unchanged.* Everything from `setup` down (D5–D20), the planning pipeline, D22, D23, inbox and judgment mechanics, `story add` with `spec_path`. A story pipeline without a `spec` step binds and runs byte-identically to today.
- *Cost if wrong.* A spec written unattended may be plausible and wrong; the review lenses and the decisions stop are the answer, and the first pilot story through this path is the proof. The spec lands on the story branch, so without the merge it is not on the working branch (as the code already is). The provisional mandate before the spec is accepted holds only the epic's acceptance lines and the `P` clauses, so a judgment at the spec step can answer under `P` clauses only.

**D25. A turn limit per role and the client stop (2026-10-19, F15).** Two parts. *The turn limit.* A pipeline role (`worker`, `reviewer`, `judgment`) may set `max_turns` (an integer from 1 to 1000; the client's own count, F19: for `claude-code` one turn is one model response, however many tool calls it holds, and the result's `num_turns` counts tool rounds), accepted only for a client whose registry entry has a `max_turns_default` (`claude-code`; `codex-cli` and `copilot` refuse it, as `worker run --max-turns` does). It is part of the pipeline digest, the launcher passes it to `run_assignment` (worker and reviewer) and `judgment.run` to `run_isolated`, and `launch.json` records it as today; without it the client's default stands (60 for `claude-code`). *The client stop.* A Claude run that ends with the result record `subtype: error_max_turns` (`terminal_reason: max_turns`, `is_error: true`, exit code 1, no `structured_output`; observed live on 2026-10-18) is a terminal receipt with a known cause and no return. For a story attempt (`bmad-implementation-v1` or the spec author) the coordinator records it as the terminal assignment state `client-stopped`: `_claude_terminal` returns a `Terminal` whose `final` is empty and whose `stop` is `{"kind": "max-turns", "num_turns": N}`; `run_assignment` accepts the non-zero exit for such a terminal, writes `last.json` empty, seals `return.json` with `result: client-stopped`, `client_stop` and no profile payload under the same scope and integrity checks as a return (a touched protected path or a changed sealed root still ends `unknown`), anchors and records it; `ReturnEvidence` carries `client_stop`; `TERMINAL_STATES` gains `client-stopped`, so the fence is released (D2) and the attempt is committed (D9: `story(<key>): attempt <n> [client-stopped]`, or an `empty` record). The implement or spec step then prepares a continuation `update` with `continues_stop` (counted in `max_updates` like the empty-attempt continuation; `update-budget` when spent) whose brief section `## Continuation after a client stop` names the earlier assignment, the stop (kind, turns), the attempt commit (or that nothing changed) and tells the worker to continue from the worktree as it stands, run the verification and return within the turn budget (the spec author: finish the spec and return), or, if the work cannot fit, return `needs-decision` with one `BLOCKED:` question that says what remains; a stopped attempt without a commit record is refused there (`BLOCKED_EVIDENCE`). A stopped attempt is never verified, bundled or reviewed. Any other profile (a planning author, a code or spec reviewer) keeps `unknown` for a client stop, with the cause in `evidence_needs`, and `run_isolated` (judgments) treats a stop as `unknown` too; every other error subtype stays `unknown`, because its cause is not known. Both runners read the stream first after a non-zero exit: a stop goes on (to `client-stopped` for a story attempt, else to `unknown` naming its cause, "the client stopped at its turn limit … without a return"), anything else keeps "Worker process exited unsuccessfully". `client-stopped` is the coordinator's own observed result (ruling H7 of the plan): `record_return` refuses it with a reported classification and refuses a `client_stop` on any other result, so `assignment return` cannot record it; at validation the stop receipt is re-derived field by field from the retained stream ("Stop receipt differs from the retained client output" otherwise).

**D26. The approval surface and the continuation brief (2026-10-19, F11, F12).** `finding_counts` (in `bmad_review`, next to `critical_open`: `{critical, high, medium, low}` counted over a review's findings and dispositions, always all four keys) joins the subjects of every accept-step stop (`spec-decisions` without a question, `critical-finding`, `open-high-findings`), for the review the stop names, and `detail review`. A continuation after a decision (`continues_request`) whose chain leads back, through request continuations only, to a correction (`corrects_review` or `corrects_verify`) repeats that correction's section in the brief after the decision lines (the same item lines, introduced as the earlier attempt's correction, still the reviewer's claims or the coordinator's red receipt); the binding's `continues` records it as `after_correction` (`{corrects_review, finding_ids}` or `{corrects_verify}`), which `_story_corrections` does not count.

## 7. Residual uncertainty

- The reversibility classification is a model claim; the fail-safe is that uncertainty stops the run. Whether a cheap model classifies well enough is what run B and later pilot runs measure.
- `--no-verify` skips the project's hooks by design; a project whose hooks generate files (formatters) will see them as verify failures, which is the intended place for them.
- Long verify suites bound the turn time; the per-command timeout and `output_limit_bytes` are the only controls in this slice.
- `max_judgments` counts the whole drive; a story with many small questions may hit `judgment-budget` before `max_corrections`. The usage example raises both budgets (there is no story default, D12); the per-step count stays a follow-up.
- The status editors handle the sprint-status shape seen in the pilot (a flat `development_status` map with `epic-<n>` keys); other shapes stop `status-shape` rather than guess.
