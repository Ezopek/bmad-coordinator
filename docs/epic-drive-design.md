# Epic drive: every remaining story of an epic, in order, on one coordinator-owned branch

Status: design approved in conversation 2026-10-18 (six sections, one question at a time; the two operator answers that shaped it are recorded in E2 and E6); implemented 2026-10-18 with fake clients (plan 2026-10-18-epic-drive, commits `97c7481`…`686a08d`; full suite 963 OK on a detached worktree of `0b8f4f1`, re-run on `686a08d` recorded in the ledger); the plan's rulings R1–R4 and the rulings made during its execution are amended into the sections below (E2, E3, E5, E6, E9–E13, §7); live verification 2026-10-18 on the pilot project (§6, live hook 18: every stop passed through, no story at `done`, so the merge, the base sync and `epic-done` are proven by the fake-client tests only; findings F11–F15); amended 2026-10-19 for F13 and F14 (E14: a story's own worker box; E15: `epic resume --restart`; plan 2026-10-19-hook-18-fixes, the execution rulings H6, H8 and H9 amended into E14 and E15) and implemented the same day on the branch (commits `b1ca87e`…`d6bdc07`, plan 2026-10-19-hook-18-fixes, 1011 tests OK on a clean worktree) with fake clients (§4, §5); live on the pilot project 2026-10-19 (§6, live hook 21, 2026-10-19 on a fixture: `epic resume --restart --roles` after an `update-budget` of client stops, three per-story turn boxes, the F17 scorer live; live hook 20: E15 restarted Story 3.3 under its own box (E14) and Story 3.4 after F18 to `done`, the base sync (E3) merged twice, `epic-done` with one story skipped). Extends the [implementation drive design](implementation-drive-design.md) (D1–D24: the story drive, its stops, inbox, resume and the spec-author step) with a loop above it. It changes nothing in how one story is driven: the story drive's pipeline, steps, stops, budgets and evidence are reused as they are, and a story driven inside an epic leaves the same records as one driven alone.

## 1. Problem

After D24 the pilot project needs, per story: `claim`, `story add` from the epic, `release`, `drive start`, the approval stops, `drive resume`, and at `done` a fast-forward of the story branch into the working branch by hand, then the next story. Three stories of the pilot's Epic 3 remain (3.2, 3.3, 3.4). Two of them carry a `**Preconditions:**` block (the pilot's convention of 2026-10-04: a story does not start until a named `deferred-work.md` entry holds a settling `decision:` line or reads `status: done`); today the spec author's brief lists the preconditions with the sentence "The coordinator does not check them", and nothing else reads them. The implementation drive design's non-goals name exactly this slice: "Sequencing several stories of an epic in one run, parking between stories" and "Merging the story branch into the target branch".

## 2. Goal and non-goals

**Goal.** One `epic start` takes every remaining story of an epic, in the order of the epics file, through the story drive's spec-author path on a branch the coordinator owns, fast-forwarding that branch after each `done`, checking each story's preconditions before it starts, and stopping with the story's own stop (and the operator's own action) whenever a story stops; `epic resume` continues the story or the loop. Success: the pilot's Epic 3 runs with one command plus the operator's decisions.

**Non-goals.** Parallel stories (one driver per repository, as today). Merging or pushing the integration branch anywhere (the operator opens the PR or merges where they point). Deleting story worktrees or branches. Stories whose spec already exists (`ready-for-dev` without the epic path): such a story stops the epic for the operator. Automatic skipping or retrying of a story. Any change to a story drive run alone (`drive start`/`drive resume` behave as before; the only visible change outside the epic is the richer `## Preconditions` section of the spec author's brief, E6). Writing `decision:` lines or sprint statuses the story drive does not already write.

## 3. Decisions

### The integration branch (E1–E4)

**E1. One run, one branch, one session.** `epic start` claims the repository once as `epic:<epic_id>` with the operator's token file, holds `drive.lock` for the whole run and, per story, syncs the base branch, checks the preconditions, adds the story (base: the integration branch), fills the pipeline template, binds and leases it under the same owner, and runs the existing driver `Run`. The session lasts across story boundaries and across stops; it is released at `epic-done` when `_releasable` allows, as a story drive's `done` is today. The operator's interventions at a stop use that one token: `bmad accept --token-file T`, `decision add --token-file T`, `inbox add decision`, `release --token-file T`.

**E2. The branch is the coordinator's.** The operator's answer (2026-10-17): the coordinator works on its own branch, created with the operator's consent from their working branch, steers it as it sees best, and at the end of the epic or sprint the operator says where the PR or merge goes. So: the branch is named by `branch` in the start input, default `coordinator/epic-<N>`; it is created at the base commit (`base`, default the `HEAD` of the worktree `--repo` names (ruling R1)) together with a linked worktree `<worktrees_dir>/epic-<N>`; an existing branch of that name or an existing worktree path is a refusal (`epic resume` continues an epic, `epic start` never adopts a branch). When `git worktree add` fails after Git created the branch, the coordinator deletes that branch (only while it still points at the base commit) and prunes the worktree record, so a retry is not refused as an existing branch. The consent is the start itself: the start summary names the branch, its worktree and the base commit. While a story runs nobody commits on the integration branch; between stories the operator may (the next story bases on the new head). The coordinator never pushes it and never merges it onward.

**E3. The base branch is tracked at story boundaries.** When `base` names a branch, the state records `base_branch`: a real branch ref (`show-ref --verify refs/heads/<name>`), or for `HEAD` (given or by default) the branch it is on. A sha, a tag, a detached `HEAD` or a revision expression such as `main~1` records `null`: no tracking and no base sync. Before every `story add`: if the base branch's head differs from `base_synced_sha`, the coordinator merges it into the integration branch in the epic worktree, `merge --ff-only` when that succeeds, else `merge --no-ff --no-verify -m "epic(<N>): sync <base_branch> at <sha12>"` with `project.commit_identity`; a conflict is `merge --abort` and the stop `integration-conflict` (E10). The merge commit is made with `--no-log`, so no `merge.log` setting rewrites its message. The conflict stop always means a clean worktree: when `merge --abort` leaves a tracked change or `MERGE_HEAD` behind, the merge is `INVALID_REPOSITORY` (the run stops `stale-input`), never `integration-conflict`. The sync and the re-listing (E5) run at every boundary, also for a `current` story without a feature, so `epic resume` after `precondition-unmet` re-checks at the new head; the exceptions are the deadline floor and the adoption of a story branch (E9). Why track: the operator's `decision:` lines and hand fixes land on their branch; the stories should build on current code; the story's baseline verify runs on the merged base before any model call and catches a regression the merge brought.

**E4. After `done`, the story branch is integrated.** In the epic worktree: `merge --ff-only story/<key>`; when the integration head moved since the story's base (someone committed there during the story), `merge --no-ff --no-verify --no-log -m "epic(<N>): merge story/<key>"` with `project.commit_identity`; a conflict is `merge --abort` and `integration-conflict`. The recorded `head_sha` of the story is the integration head after the merge. Every Git write of the epic goes through the isolated Git of the receipts (`_git_run`: hooks off, allow-listed environment, `LC_ALL=C`), after the same branch-identity check the story commits make: the epic worktree must have the integration branch checked out and a clean tree, else the stop `worktree-drift` of the epic (E10).

### Stories and their preconditions (E5–E7)

**E5. The story list.** The `### Story N.M:` headings of the epics file under epic N, in file order; each maps to the one `development_status` key of `sprint-status.yaml` (read at the integration head) that starts with `N-M-`. A heading with no key or with several, or a key whose status is neither `backlog` nor `done`, is the stop `story-status` naming the story and what was found. `done` stories are recorded as already done and skipped; `backlog` stories are pending. The list is computed at start and again at every boundary (the operator may change statuses between stories). The last story's status commit flips `epic-N: done` as it does today (D18); the epic driver writes no sprint status itself. A story the listing cannot place is recorded `blocked` with the reason (ruling R4); `--skip` turns it `skipped`; every later listing re-classifies a `blocked` story.

**E6. Preconditions: a mechanical gate, the spec author's judgment behind it.** The operator's answer (2026-10-18): mechanical plus the spec author's judgment, not a human question per precondition and not a judgment model. The bullets of the story's `**Preconditions:**` block (already in the mandate, `parse_epic_story`) each name an entry `DW-<n>`. At the integration head, after the base sync, the helper `preconditions_state(repo, commit, artifacts_dir, bullets)` reads `<artifacts_dir>/deferred-work.md` and `<artifacts_dir>/deferred-work-archive.md`, finds the entry by its heading `### DW-<n>:` and the field lines directly under it, and decides per bullet: **met** when the entry's `status:` line reads `done …`, or the entry has a `decision:` line whose option label does not start with `keep-open` or `keep open` (in any case) and no `decision:` line whose label does (the deferred-work format: a keep-open decision leaves the entry open, and the convention says such a decision does not settle; a settling line beside a keep-open one, in either order, is unmet as `conflicting decision: lines`, so a later sweep's keep-open is never outvoted); the option label is the line's value less one leading `YYYY-MM-DD` date, cut at the format's ` — <detail>` separator and less its leading punctuation and markup (`` `keep-open` ``, `"keep-open"` and `**keep-open**` read `keep-open`; a line that is only `— <detail>` has no option), and a dateless or empty decision follows the same rule (a label starting with `keep-open` or `keep open`, in any case, or no option, never settles); **unmet** otherwise (no settling line, conflicting decision lines, no entry, a bullet naming no id, an unreadable ledger, a malformed entry: a repeated `### DW-<n>:` heading in the ledger or more than one `status:` line, each with the reason). The ledger is read first; in the archive, which appends, the last block of an id counts. Any unmet bullet is the stop `precondition-unmet` naming the story, the entry and the bullet; the story is not added. The helper never raises on ledger content: a malformed ledger is "unmet, <why>".

The same helper feeds the spec author's brief and the spec reviewer's brief: the `## Preconditions` section lists each bullet followed by the entry's `status:`, `decision:` and `resolution:` lines as read at the attempt's base commit, and the sentence "The coordinator does not check them." becomes "State at `<sha12>`: <met/unmet per bullet>. A decision that does not settle its precondition, or a change it requires in this story that the epics entry does not show, is an Open Question, never an assumption." This holds for a story driven alone too. What stays human: "any change that decision makes to this story is applied here" (the epics entry's amendment); the author reads the entry at the head, so an amendment is seen and its absence is asked.

**E7. The story is added and run under the epic's owner.** `story_add(repo, store, owner, StoryInput(spec_path=None, story_key=<key>, base_ref=<integration branch>, worktree=<worktrees_dir>/story-<key>, writable_scopes, project_clauses, epic_story={epics_path, story_key}))`: scopes and clauses come from `stories.<key>` in the start input, else from `story_defaults`. A `DomainError` from `story add` (a `story/<key>` branch that exists, a worktree path that exists, a key the epics file lacks) ends the epic `failed` with reason `story-add` and the message; `story add` has rolled back its own writes. Then the template is filled (E8), `drive_pipeline.validate` and `check_bindable` run on the filled pipeline, `bind` seals it, a lease is sealed and anchored as `drive start` does (plus `epic_id`), and `Run(repo, store, owner, lease, pipeline, bounds, clock, "start")` executes with `release_on_done=False` (the epic, not the story, releases). A story driven this way is indistinguishable in the store and in `drive status` from one driven alone, except for `epic_id` in its lease.

### Pipeline template, bounds, state (E8–E9)

**E8. The template.** A story pipeline as today whose `feature_id` is the token `__FEATURE__` and whose step `story` blocks use `__KEY__` (in `story_key`, and inside `spec_path`, e.g. `<artifacts_dir>/spec-__KEY__.md`). Filling replaces both tokens in every JSON string value. `epic start` validates the template once by filling it with sample values and calling `drive_pipeline.validate`; it refuses a template without a `spec` step (every epic story is a D24 story) or with `mandate_revision` other than 1. The template is sealed as `epics/<epic_id>/template.json`; the filled pipeline of each story is sealed by `bind` as today. `accept_on_high` is the template's and `judgment_root` and `human_wait` are the start flags', for every story.

**E9. State and bounds.** `<common-dir>/coordinator/epics/<epic_id>/state-<n>.json`, sealed and anchored (`epic.started` for `state-1`, `epic.advanced` for each later one, `epic.ended` for the summary); the newest anchored state is the truth, as a lease and its summaries are today. Fields: `kind: epic-state`, `format: 1`, `revision`, `epic_id`, `repository_id`, `generation`, `epics_path`, `epic` (the epic's number), `branch`, `worktree`, `worktrees_dir`, `base_ref`, `base_commit`, `base_branch` (or null), `base_synced_sha`, `head_sha`, `template_ref`, `template_sha256`, `judgment_root`, `bounds`, `story_defaults`, `stories_input` (the start input's per-story overrides), `stories` (list, epics order: `{number, title, key, state: pending | current | done | skipped | already-done | blocked, feature_id, base_sha, lease_id, run_id, outcome, reason, head_sha, detail}`, each field once it is known, `detail` for a `blocked` story; a story is `current` from the moment the loop picks it, before its gate, so a precondition stop leaves it `current` without a feature), `created_at`, `advanced_at`. Every transition (a sync merged, a story added, a story's run ended, a story merged, a skip) anchors a new state before the next Git write; the resume reconciles the integration head with the record: a story whose run ended `done` but whose `head_sha` is unset is merged now if its branch is not yet an ancestor of the integration head, and recorded if it already is. Bounds: `--deadline` is the whole run's (each story run gets `RunBounds(max_turns, deadline=remaining)`, with the driver's `MARGIN` as today), `--max-turns` is per story run; `epic resume` takes new bounds, default the start's with the deadline counted from the resume. At a boundary the deadline floor (the template's largest role timeout plus `MARGIN`) is checked before any sync, listing, gate or `story add`: under it nothing is synced, gated, added or leased and the run ends `continue` (`deadline`); the listing still runs, so a finished epic ends `epic-done`. Ruling R2 depends on this order: a deadline stop after `story add` would leave a story with a feature and no ended run, which the skip refuses. A `current` story without a feature whose `story/<key>` branch already exists (a kill after `story add`, before its state) is adopted without a sync, a listing or a gate at that boundary, so a moved base cannot make its own branch look foreign; the sync happens at the next boundary. The summary's `counts` are the run's (a start or a resume), not the epic's.

### Stops, resume, status (E10–E13)

**E10. Stops and exit codes.** A story run's outcome ends the epic run with the same `outcome` and `reason`, the story's `subjects` with `key`, `feature_id`, `lease_id` and `run_id` added, and the same exit code (`done` 0, `continue` 10, `needs-human` 11, `failed` 12); its `operator_action` is built with the command name `epic` (`… then epic resume`), which `_operator_action` takes as a parameter (ruling R3: `drive resume` becomes `epic resume`, the rest of the story's text stands; the summary's second field `epic_action` names the epic-level options: the skip under R2, and after a `release` the re-claim of E12). The approval stop's third option (release and revise attended) stays worded as today; after a release the epic continues only through E12. Epic-level reasons, all `needs-human`: `precondition-unmet` (story, entry, bullet; action: record the decision on the base or the integration branch, then `epic resume`, or `epic resume --skip <key>`), `story-status` (key, status found; action: finish or re-status it by hand, or `--skip`), `integration-conflict` (which merge, the conflicting paths; the epic worktree is clean after the abort; action: `git -C <epic worktree> merge <ref>` by hand, commit, `epic resume`, which recognises the done merge), `worktree-drift` of the epic worktree (what differs; action: restore the branch, clean the tree, `epic resume`). Whether a stop is the epic's or the story's is decided by its origin (the loop or the story run), not by the reason's name: `worktree-drift` exists on both levels, and a story run's keeps the story's text. `epic-done` is `outcome: done` with every story `done`, `already-done` or `skipped` (the skipped ones listed). A `failed` story outcome (`ownership-lost`, an invalid pipeline) ends the epic `failed` with that reason and no Git write. Signals: the story run's graceful `signal-stop` as today; the epic ends with it. The epic summary (`kind: epic-summary`, anchored `epic.ended`) carries the epic (branch, head, the stories' states), the current story (key, feature, lease, the run summary's ref), outcome, reason, `operator_action` and counts (stories done and skipped, merges, syncs).

**E11. Resume.** `epic resume --token-file T [--skip KEY] [--max-turns N] [--deadline S] [--human-wait S] [--judgment-root P]`: `drive.lock`, the token fence, the epic from the owner session `epic:<id>`, its newest state. A `current` story whose lease's last run is not `done` resumes with `Run(..., "resume")` of that lease (the lease's pipeline, the bounds as above); otherwise the loop continues (reconcile, sync, re-list, next story). `--skip KEY` applies to the story the last stop named: `current` without a feature yet (the precondition case) or `blocked` (the `story-status` case, ruling R4); a story with a feature is skipped only once its last run ended `needs-human` or `failed` and no attempt of it holds the fence (ruling R2: the story's feature, branch and worktree stay for the operator; nothing of it is merged). `drive resume` with an epic session is the refusal `epic-session` naming `epic resume`; `drive start` and `epic start` on an owned repository are `OWNERSHIP_CONFLICT` as today.

**E12. After a release.** `epic resume --epic ID --token-file NEW` when no session owns the repository: claims as `epic:<id>` under a new generation, records it in a new state, re-seals the current story's lease under that generation (as the D24 carry re-seals a lease) and continues at E11. A lease the loop reuses whose generation differs from the owner's (a kill between the lease and its state, then a re-claim) is re-sealed the same way first. This is the path after the operator released to work attended; the pilot run is not expected to use it (§7).

**E13. Status and CLI.** `epic status [--epic ID]`, read only, no token: for the epic (or every epic of the repository, newest first) the branch, head, `base_synced_sha`, the stories table (state, feature, outcome, head), the `drive status` entry of the current story's feature (with `--epic` only) and the last summary's `operator_action`. `epic start --token-file T --pipeline TEMPLATE [--max-turns N] [--deadline S] [--human-wait S] [--judgment-root P]` reads one JSON object on stdin: `{"epics_path", "epic": N, "branch"?, "base"?, "worktrees_dir", "story_defaults": {"writable_scopes", "project_clauses"?}, "stories"?: {"<key>": {"writable_scopes"?, "project_clauses"?}}}`. The lesson of F9 applies to `story_defaults.writable_scopes`: wider than one story needs, with the paths a story may touch by convention (`.env.sample`, docs); a story's own scopes override.

**E14. A story's own worker box (2026-10-19, F13).** The start input's `stories.<key>` override takes a third key `roles`: `{<role>: {timeout?, max_turns?}}` for roles the template names, within the pipeline's own ranges. `fill_template(template, feature_id, key, roles)` merges each override over the template's role before validation, so the story's sealed pipeline carries the merged roles and its digest differs from the other stories'. `epic start` validates every override by filling the sample with it and checking the bounds (every refusal names the story; `bounds-insufficient` for a box the deadline cannot hold); `epic resume` validates only the overrides of stories still to run (not `done`, `skipped` or `already-done` in the newest state, and not the story a `--skip` or a `--restart` names; a restart checks the story's effective override itself, E15), so a finished story's box never blocks a shorter later run (ruling H6 of the plan, amended for the restart). The deadline floor at a boundary is checked with the template's sample before the sync and again with the picked story's merged pipeline before its add, so a story with a wider box ends the run `continue`/`deadline` only when its own box no longer fits. The override lives in `stories_input` (the sealed state) and a restart's `--roles` sets or replaces it (E15). The budget stays the operator's: nothing widens a box by itself.

**E15. Restart of a story inside the epic (2026-10-19, F14).** `epic resume --restart KEY [--roles PATH]` applies to the story the last stop named under the conditions of `--skip` (the restart target is left out of the resume's override check, E14; `restart` checks the story's effective override itself; ruling H10 of the plan: a restart follows a terminal stop of the story's last run — `critical-finding`, `open-high-findings`, `correction-budget`, `update-budget`, `worker-blocked`, `attempt-resolved` — and any other stop is refused naming its designed path, a decision or an accept, and the summary advertises `--restart` for those reasons only) (a `current` story with a feature, a last run that ended `needs-human` or `failed`, no attempt holding the fence, no recorded restart still to run; `restart-refused` otherwise, the pending restart as "… has a restart pending; epic resume runs it first", which refuses `--skip` too; `--skip` with `--restart` and `--roles` without `--restart` are `INVALID_INPUT`). The epic (a) records the story's restart count `restarts` (n, one above the highest `epic-restart:<n>` decision the feature already holds, so a feature from an earlier epic never collides) and the optional roles override (a JSON file `{<role>: {timeout?, max_turns?}}`, E14) in the next state revision, with the story's `lease_id`, `outcome`, `reason` and `run_id` cleared; (b) records an operator-reported decision `epic-restart:<n>` at the feature's mandate revision and revises the mandate with `constraints.restarts = n` and `constraints.restart_carry` (ruling H8 of the plan: the terminal stop's evidence for the new revision's briefs — the blocking items of the review a `critical-finding` or `open-high-findings` stop names (its `finding_ids`, else the critical and high items), or the failed command names of a `correction-budget` stop's red receipt, nothing for any other stop; both story briefs (the implement brief and the spec author's) render it as `## Carried from the restart` on every brief of that revision, corrections and continuations included, JSON-quoted, as the earlier revision's recorded claims, not decisions; the review briefs do not, a restart without a carry drops an older one, and a spec carry to a later revision replaces the constraints and so drops it); a kill between (a) and (b) is finished at the next resume: before a story is leased, `_restart_pending` looks for the decision `epic-restart:<n>` (ruling H9: no decision → record and revise; a decision at the feature's current revision → revise; a decision below it → done), never for `constraints.restarts`, which a later carry replaces; (c) binds the template filled for the story (merged roles) at the new mandate revision under the epic's session as a new lease and runs it as a start. The new revision sees no earlier attempt (the chains are per revision, ruling P5 of the spec author plan), so its corrections and updates start at zero and its first implement attempt is a create standing on the branch as it is: the attempt commits, and any uncommitted files the operator left after `attempt resolve`, are taken by the next attempt commit (the hand-fix precedent of `correction-budget`). The spec chain stays satisfied by the `spec` status receipt (ruling R5), so a restart after the carry does not rewrite the spec; a restart before the carry runs the spec chain again at the new revision. `_lease` reuses the feature's newest anchored lease only while its `epic_id` is this epic's and its pipeline's `mandate_revision` is the feature's current one, and otherwise binds anew; that rule is what makes the restart, and a kill inside it, resume correctly (a carry in flight never reaches `_lease`: it keeps the story's `lease_id` set, so the story drive's own run finishes it). The summary's `epic_action` names `--restart` beside `--skip`, `counts.stories_restarted` counts this run's restarts and the story record carries `restarts`. No cap: every restart is the operator's word.

## 7. Residual uncertainty

- E12 (resume after a release, re-sealing the current story's lease under a new generation) follows the carry's precedent but is the least exercised path; the pilot run does not plan to use it. If the plan finds the re-seal unsafe for a story with an attempt in flight, the fallback is to refuse E12 while the current story has an unobserved assignment. That case cannot arise: `release` itself requires D2, so no unobserved assignment can be running when the epic is re-claimed.
- The `keep-open` label is the deferred-work format's one example of a non-settling decision; another wording that keeps an entry open passes the mechanical gate and is left to the spec author's Open Question.
- The coordinator's merge commits on the integration branch are its first commits outside a story branch; the branch-identity check (E4) and the sealed state before every write are the guards. A merge whose result fails the next story's baseline verify stops that story as `verify` does today, not the epic.
- Story worktrees accumulate (one per story, `project.setup` per worktree, e.g. a `node_modules` link in the pilot); cleanup stays the operator's.
- One epic at a time per repository (the owner session); a second epic is `OWNERSHIP_CONFLICT`.
- A kill between `create_integration` and the first anchored state leaves the integration branch and its worktree with no record to resume from (`epic resume` refuses `run-unbound`, the session is still claimed): the operator releases the session, removes the worktree and the branch by hand (`git worktree remove`, `git branch -D`) and runs `epic start` again with a new token file.
- **F14 (live hook 18).** A story that stops `critical-finding` or `correction-budget` with its budget spent, or `attempt-unknown`, has inside an epic only `--skip` or `release` plus an attended finish: `drive start` of a pipeline bound to a new mandate revision makes a lease the epic does not own, `drive resume` with the epic's token is refused (`epic-session`), and after `attempt resolve` the step stops `attempt-resolved` and asks for a hand-prepared attempt. Candidate: `epic resume --restart KEY [--pipeline T]`, which revises the current story's mandate, binds a new pipeline under the epic's lease with corrections at zero and prepares the next attempt itself. Resolved 2026-10-19 (E15): `epic resume --restart KEY [--roles PATH]`; the candidate's `--pipeline T` became the per-story roles override (E14), so the template stays one per epic.
- **F17 (live hook 19, 2026-10-19; the scoring harness).** `tests/drive_support.unattended_checks` scores a whole epic from the main repository as `fail`/`blocked` on its story criteria (`worker-observed-complete`, `review-observed-bound`, `attempt-committed`, `verify-observed`, `status-synced`) because they assume one story feature per repository and re-validate returns against the repository they are given, while an epic's attempts ran in the story worktrees; scored per story from each story worktree every criterion passes. Test support only, no product change: an epic-aware scorer (one feature per lease, each from its worktree) is a follow-up. Resolved 2026-10-19: `tests/drive_support.epic_checks(repo, epic_id)` scores every story of the epic's newest state from its own worktree with its leases and merges per criterion (`fail` > `pass` > `trivial` > `blocked`).
- **F20 (live hook 21, 2026-10-19; a spec-phase judgment after the carry).** `judgment.verdict()` validates the cited clause against the feature's current mandate, and the spec → implement carry revises the mandate (the spec's `S` clauses precede the project's `P` clauses), so a judgment that answered a spec author's question at revision 1 reads `valid: false` at revision 2 while its recorded decision stands (`record` refused anything invalid at its own revision); `judgment status` shows the same. The scorer (`judgment-backed-decision`) now requires `valid` only for a decision at the feature's current revision and checks the verdict's revision against the decision's. The product reading is a candidate: validate against the sealed `mandate.json` the judgment was given (its digest is in the request record) when the revisions differ.
