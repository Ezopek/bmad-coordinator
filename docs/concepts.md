# Concepts

This page explains the words the coordinator's commands, stops and receipts use, in the order you meet them. [Getting started](getting-started.md) shows the commands; the [usage reference](state-core-usage.md) has every flag and limit; the design documents linked from the [README](../README.md#repository-layout) record why each rule exists.

## The repository and its state

The coordinator keeps all its state inside the Git repository it drives, under the common `.git/` directory in `coordinator/`: a SQLite database (`state.sqlite3`, the canonical local state) and directories of receipts beside it. `init` creates it. Every linked worktree of the clone shares it, so a story worktree and the main checkout see the same state; a second clone of the same project has its own and knows nothing of the first. BMAD's own files (`epics.md`, `sprint-status.yaml`, `deferred-work.md`, the specs) stay authoritative for their content: the coordinator records references and digests, and edits only the status fields it owns. Nothing under `.git/coordinator/` is meant to be edited by hand; a changed sealed file reads back as `unknown`, never as something better.

## Owner session, token and generation

One session owns the repository at a time. `claim`, `drive start` and `epic start` take ownership: they write a private token file (mode `0600`, created exclusively, never overwritten) holding a random token and the owner *generation*, a counter that grows with every claim. Every command that changes state takes `--token-file` and checks the token and the generation in the same transaction; a stale token, an active owner or a second claim is `OWNERSHIP_CONFLICT` (exit 3). A command that only reads (`status`, `epic status`, `drive status`, `detail`, `verify`, `inbox list`) needs no token. `release` ends ownership; it refuses while an attempt still needs lifecycle evidence. The session is named by its kind: `drive:<lease id>` for a story drive, `epic:<epic id>` for an epic. A running driver also holds an exclusive lock on `drive.lock`, and every token-fenced command a shared one, so a driver and a fenced command refuse each other instead of racing. The token file is local ownership material: it stops two sessions on one computer from both driving the repository, and nothing more.

## Feature and mandate

A *feature* is the unit the coordinator drives: an immutable id, a branch, a base commit, a linked worktree, the writable scopes a worker may touch, and a *mandate*. The mandate records the outcome, the constraints, the exclusions, the completion criteria and the *authority*: `authority.delegated`, a numbered list of clauses a judgment may cite when it answers a question in your place. A story is a feature (`story add`): its mandate is read from the spec's frozen section, line by line (`S1`, `S2`, …), followed by your project clauses (`P1`, …). A story added from its epics entry carries a provisional mandate (the entry's title, user story, acceptance lines and preconditions, with the project clauses alone as authority) until its spec is accepted. The mandate has a *revision*. A pipeline is bound to one revision, and anything that revises the mandate (the carry after the spec is accepted, a restart inside an epic) binds the pipeline again at the new revision; attempts, corrections and updates are counted per revision.

## Assignment, attempt and the brief

An *assignment* is one bounded piece of delegated work, recorded before anything is launched: the feature and its mandate revision, the author id, the *brief* the worker will read, the writable paths, the digests of the inputs it was given, the client. An *attempt* is one launch of a client for that assignment: one process, in the feature's worktree, with the brief, a time box (the role's `timeout`) and, for Claude, a turn limit (`max_turns`). The brief is rendered from stored rows, never from free text a caller typed: the frozen section, the clauses, the recorded decisions, the verify commands, the rules and, for a continuation, what it continues. The attempt ends with a *return*, one structured JSON object the coordinator validates: `completed`, `needs-decision` (one question with options; a condition the worker cannot change is a question starting with `BLOCKED:`), `blocked` (a brief it could not read), or, for a Claude story attempt, `client-stopped` (the client's turn limit). A process that ends without a valid return leaves the attempt *unknown* with its fence held (see [Runs, turns and stops](#runs-turns-and-stops)).

Attempts form a *chain*: a later attempt continues an earlier one after a decision, after an empty attempt or after a client stop (an *update*, counted in `budgets.max_updates`), or corrects it after a red verify or a blocking review (a *correction*, counted in `budgets.max_corrections`). The coordinator commits every terminal attempt of a story as it stands, `story(<key>): attempt <n> [<result>]`, hooks off, never squashed, so the chain is readable in `git log`.

## Verify, bundle, review and acceptance

Four coordinator steps turn a worker's claim into something checked:

- **Verify.** Your `project.verify` commands run on the attempt commit, in the story worktree, each under its own timeout, and the receipt (exit codes, captured output, digests) is sealed. A green receipt is the precondition of the bundle; a red one triggers a correction while the budget lasts, then the stop `correction-budget`.
- **Bundle.** A content-addressed, read-only copy of the changed files with a manifest (paths and digests, the commit, the mandate revision, the contributing assignments, the decisions that resolved their questions), sealed under `.git/coordinator/bundles/`. The reviewer reads the bundle, not the moving worktree, so a review names exact bytes.
- **Review.** A separate attempt by the `reviewer` role, with no write tools, against the bundle and a fixed set of lenses (`acceptance`, `matrix`, `scope`, `security`, `regression` for code; `readiness`, `scope`, `verification`, `edges`, `fidelity` for a spec). Its findings carry a severity: `critical` blocks acceptance; `high` blocks unless the pipeline sets `accept_on_high`; `medium` and `low` are listed. A review is *observed* only when a distinct process returned an anchored structured result that names the sealed bundle exactly; what the findings say is the reviewer's claim.
- **Acceptance.** A record that names the bundle and the review. It is *current* while the bundle still describes the branch: HEAD on the story branch at or above the commit, the newest verify of that commit green, the scopes clean. A later change makes it `stale` or `unknown` in `verify`; the historical record stays.

## Questions, judgment and decisions

A `needs-decision` return opens a *request*. The driver resolves it in one of two ways, and either way records a *decision* row with its `source_kind` (`coordinator` or `operator-reported`), a `source_ref` that names the clause or the receipt it rests on, and the request it resolves.

The *judgment* is a model call of its own (the `judgment` role), run in the judgment root, isolated from the worktrees, with the mandate, the question and the clauses. It may answer only by citing, for every answer, one clause: the clause id, its JSON pointer and a verbatim quote of at least 24 characters, all checked against the mandate at the bound revision; an answer that cites nothing that exists is a refusal. On a story it runs under schema v3: a reversible choice it cannot cite a clause for may be *deferred* (the minimal choice closest to the frozen story, recorded as a decision and written to `deferred-work.md` at `done`), while a *binding* question (persisted data, external contracts, security, user-visible behaviour beyond the intent, deleting or renaming public things, new dependencies, anything a later change cannot undo) or an uncertain one is refused, and the run stops `product-decision` (`spec-decisions` for the spec author). On a story, a request with several questions is sent back to the worker to ask one at a time, without a judgment. `budgets.max_judgments` bounds the calls per run. The judgment's correctness stays a model claim: the code proves that a distinct process returned a verdict whose every citation exists in the mandate, not that the clause means what the judgment says.

You answer through the *inbox*: `inbox add decision` writes one private immutable file that the driver consumes at its next turn boundary (or while it waits with `--human-wait`); your answer preempts an unused judgment. An inbox decision written while an attempt or a judgment window is open is rejected and must be re-sent once the window has closed.

## Runs, turns and stops

A *lease* is one driver's hold on one feature's pipeline; a *run* is one foreground execution of it (`drive start`, then every `drive resume`); a *turn* is one iteration of the loop: reconcile the evidence, derive the state of every step from rows and receipts, take at most one action (a launch, a commit, a verify, a bundle, a review, a decision, a status edit), record it. `--max-turns` bounds a run in turns and `--deadline` in seconds. A run ends with one summary and one of four outcomes: `done` (exit 0), `continue` (10: a bound was reached; resume), `needs-human` (11), `failed` (12: ownership lost, no progress, corrupt state, an internal error).

A `needs-human` *stop* has a closed `reason` and an `operator_action` written for that reason; the [getting started](getting-started.md#stops) table lists the first ones, [troubleshooting](troubleshooting.md) the causes, and the usage reference every one. Some stops are answered by an inbox decision or an accept and a plain resume; some are terminal for a plain resume (`worker-blocked`, `correction-budget`, `update-budget`, a review that still blocks with the corrections spent) and need a new attempt chain: inside an epic, `epic resume --restart <key>` revises the mandate and starts one. A killed or stalled attempt stays *unknown* with its *fence* held: no new attempt of that feature launches until you say what happened (`attempt resolve … --confirm-unknown`), because the fence is released on operator evidence only.

## The story pipeline

One story runs these steps in this order; each is satisfied by a sealed receipt, so a killed run resumes from the last one.

1. `spec`: the spec author writes `spec-<key>.md` from the epics entry, your context files and the house rules. `spec-bundle`, `spec-review` and `spec-accept` review and accept it (by you at a `spec-decisions` stop, or by the driver with `spec_auto_accept`). `spec-ready` commits the spec as `ready-for-dev` and the driver *carries* the story: the mandate is revised from the accepted spec, and the same pipeline is bound at the new revision.
2. `setup`: your `setup` commands, then every `verify` command on the base commit (the *baseline*). Nothing is launched before a green baseline; a red one stops `verify-env`.
3. `start`: the status files flip to `in-progress`, committed by the coordinator.
4. `impl`: the worker implements the spec. `impl-commit` commits the attempt; `impl-verify` runs your commands; `impl-bundle`, `impl-review` and `impl-accept` as above. Questions, continuations and corrections loop inside this group.
5. `finish`: the status files flip to `done`, the spec gets a `## Coordinator Result` section, and `deferred-work.md` gets one entry per deferred choice and per accepted open `high` finding.

The spec lives at `_bmad-output/implementation-artifacts/spec-<key>.md`, the briefs under `_bmad-output/coordinator/briefs/`, both on the story branch. The status commits carry the trailer `Coordinator-Status`, the attempt commits `Coordinator-Assignment`.

## The epic loop and the integration branch

`epic start` claims the repository once, creates the *integration branch* (`coordinator/epic-<N>` by default) at the base commit with its own worktree, and loops over the epic's stories in the epics file's order. Per story: if `base` named a branch and it moved, merge it into the integration branch (`--ff-only`, else a `epic(<N>): sync …` merge commit); list the stories again (`done` ones are skipped, anything but `backlog` or `done` stops `story-status`); check the story's `**Preconditions:**` bullets against `deferred-work.md` (stop `precondition-unmet`); add the story as a feature on branch `story/<key>` from the integration head, in `<worktrees_dir>/story-<key>`; fill the template (`__FEATURE__`, `__KEY__`, the story's own `roles` box) and run the story pipeline as a lease of the epic's session. At `done`, merge `story/<key>` into the integration branch (`--ff-only`, else `epic(<N>): merge story/<key>`); a conflict stops `integration-conflict` with the epic worktree clean. A story's stop passes through unchanged with its `key` added; `epic resume` continues the story or the loop, `--skip` leaves a stopped story to you, `--restart` starts a new chain for it. `epic-done` releases the session. The coordinator never pushes the integration branch and never merges it anywhere: that is your pull request.

## Evidence: observed and claimed

Every step leaves a *receipt*, a file under `.git/coordinator/` whose digest is recorded in an anchored event in the database (*sealed*): `runs/<run>/` (the launch record with the exact argv and the environment variable names, the client's retained stream, the return), `bindings/` (what each attempt was given), `story/<feature>/` (setup, baseline, commit records with their patches, verify, status), `bundles/`, `judgments/`, `drives/<lease>/<run>/` (one `turn-*.json` per turn, the summary), `epics/<id>/` (the states and summaries), `inbox/`. `detail`, `verify`, `drive status` and `epic status` read them back; the summary's `unattended_checks` scores a run against them.

Two words recur in those records. *Observed* means the coordinator's own evidence: a distinct process it launched returned a structured result under the session id it preset, the result validates, the Git delta of the worktree is what it is, the verify commands exited as recorded. A *claim* is what a model wrote: the worker's `tasks`, `verification` and `notes`, a reviewer's findings, a judgment's rationale, the cost a client reported (`client_facts`). Claims are kept verbatim and marked; nothing upgrades a claim to an observation. When evidence is missing or a sealed file changed, the record reads `unknown`, and `unknown` never means failed or passed: it means you have to look.
